# 查经准备

设计见 `docs/wang-knowledge-platform/60-reference-commentary/bible_study_prep_solution_v1.md`。那里的每一条规则，都来自 2026-09-25 那次（马太 19:27–20:34）手工做时出过的问题。

所有命令在仓库根目录跑，用仓库的 Python：`.venv/bin/python`。`DATA_BASE_DIR` 和知识库连接都从仓库的 `.env` 读。

## 1. 开始或接着做

**带参数**（`/bible-study 2026-10-02 太 20:28`）：

```bash
.venv/bin/python -m backend.bible_study.sources 2026-10-02 "太 20:28"
```

它建好 `$DATA_BASE_DIR/bible-study/2026-10-02-mat-20-28/`，写 `sources.json`，缓存和合本。把它打印的摘要告诉负责人：Carson 几页、哪几页讨论这段经文、有没有没扫描的章或缺页；教授几条 claim、来自哪几篇讲道。**Carson 缺章就先请负责人扫描**，不要在没有材料的情况下开讲。已有 `sources.json` 时它不覆盖（负责人可能手改过），要重建加 `--refresh`。

**不带参数**：

```bash
.venv/bin/python -m backend.bible_study.check status
```

列出各次查经和进度。请负责人选一个，然后读回该目录里的 `notes.md`、`outline.md`、`script.md`，说明做到哪一步、下一步是什么。**准备档是跨会话的唯一记忆**；对话会结束、会被压缩，文件不会。

## 2. 材料

- **Carson**：`$DATA_BASE_DIR/reference-commentary/<volume_id>/text/` 下的页文件（每页多个版本时取 `pages.json` 里 `text` 指向的那个）。只在会话里读、回答问题。**绝不整页或大段输出原文**：Claude 逐字输出受版权保护的书页会被内容过滤拦下，整个会话作废（2026-09-23 发生过）。引用只取一句，标明「Carson, EBC Matthew, v. 2, p. 431」。新扫描的页由收件夹的 Gemini 任务转写，不在会话里转写照片。
- **教授**：`sources.json` 里的 claim 和讲道名。需要上下文时读讲道原文。教授的话进纪要时写 `claim <claim_id>`。
- **经文**：和合本（繁体）缓存在 `$DATA_BASE_DIR/bible/cuv/<书卷>/<章>.json`。

## 3. 提问与解答：每个结论记一条纪要

和负责人一问一答。每得出一个结论，**当场**追加到 `notes.md`，并告诉负责人编号（「记为 n12」）：

```markdown
## n12 · 待定 · 「用人」與「僕人」是兩個詞
- 問：26 節和 27 節的「用人」「僕人」有甚麼分別？
- 結論：……
- 依據：carson v2 p432；claim DK-…；太 20:26-27
```

- 状态：`採用`／`不用`／`下次講`／`待定`。新记的一律 `待定`，由负责人定；负责人一表态就改
- `依據` 必填：Carson 页码、`claim <id>`、经文，负责人自己的看法写「負責人」。分清谁说的
- 负责人自己提出的见解同样记，依据写「負責人」（2026-09-25 最好的几点——右边左边在十字架上、「要得甚么」对「不知道所求的」——都是负责人提的）
- 编号只增不改，不重用

## 4. 范围与大纲：批准后才写逐字稿

根据**三样材料**起草 `outline.md`：Carson 相关页、教授相关讲道、`notes.md`。先定范围，再定大纲：

```markdown
# 範圍
馬太福音 20:17–34，線上查經約一小時。……
留到下次：20:28「作多人的贖價」……
<!-- deferred: n16 n25 -->

## 五、座位與服事
十個門徒也一樣；不可這樣；用人到奴僕；……
<!-- notes: n18 n19 n20 | sources: carson v2 p432；太 20:24-28 -->
```

交给负责人改。检查：

```bash
.venv/bin/python -m backend.bible_study.check <目录名> --stage outline
```

`待定` 的纪要要先请负责人定；`採用` 的每条都要分到某一节；`下次講` 的都列进 `deferred`。负责人明确批准后，在第一行加 `<!-- approved: YYYY-MM-DD -->`。**没有这一行不写逐字稿。**

## 5. 逐字稿：一节一节写

**一次只写一节。** 2026-09-24 一次生成整份，讨论过的服事一段整段漏掉。每节：先列出这节要讲的纪要，负责人点头，写这一节，存进 `script.md`，给负责人看，再下一节。

- `##` 标题与大纲一字不差、顺序一致
- 承载纪要的段落末尾加 `<!-- n12 n13; carson v2 p432 -->`；渲染时看不见
- `下次講` 的纪要最多一段预告，不展开

写法（负责人 2026-09-24 定的，机器不查，自己守）：

- **带领人自己的话**。不引用、不提教授的讲道；教授的观点用自己的话讲出来
- **中心真理正面点明**，单独成段，不要只是暗示（葡萄园那次：「我们得到的就是恩典」要明说）
- 语气平和；对象是信主多年的弟兄姊妹，线上，一小时
- 正文繁体，经文用和合本原文
- 讨论题少，一两题即可
- 给带领人的附注（出处、推测性的说法、有人问才答的问题）放在文末 `---` 之后

每写完一节跑一次：

```bash
.venv/bin/python -m backend.bible_study.check <目录名>
```

## 6. PPT

负责人对 PPT 的四条要求：

1. **字体要够大，要清晰**
2. **逐字稿中引用的经文都要出现在 PPT 上，而且不能简化**
3. **PPT 要 cover 逐字稿的所有内容，不能跳过**：每个要点都在某一页上
4. **每张投影片只呈现要点**：短句，不是逐字稿的句子；完整的话放备忘稿和对照文件

具体做法（字号、zh-TW 断行、经文拆页、关键经节、表格行高、PowerPoint 渲染检查……）见设计文档 5.1 节的十四条，一条都不能丢。生成器在 `tools/bible-study-ppt/`（WKP-F11.07）；在它进仓库之前，用 `$DATA_BASE_DIR/bible-study/_generator-snapshot-2026-09-25/`。

## 7. 发布

复制 `.pptx`、逐字稿和（投影片對照）.md 到 `$DATA_BASE_DIR/fellowship/docs/<日期>/`（即 OneDrive `团契/<日期>/`，网站公开可下载）。

**复制前先查目标文件是否在 PowerPoint 里开着**；开着就停下，请负责人关掉（不要存）再继续。2026-09-25 负责人开着旧版，以为新版页码错了。

发布后告诉负责人每个文件的位置，和 PPT 的页数。
