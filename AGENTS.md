# Wang Knowledge Platform session boundary

When the task concerns Matthew exposition articles or Wang repository content production, `docs/wang-knowledge-platform/` is authoritative. Read these files before acting:

1. `docs/wang-knowledge-platform/CURRENT_AUTHORING_SESSION.md`
2. `docs/wang-knowledge-platform/matthew_exposition_multi_agent_authoring_workflow_v1.md`
3. `docs/wang-knowledge-platform/fast_passage_editorial_workflow_v1.md`

Do not import gates or maintenance operations from `docs/notes-to-sermon-agent/` into this workflow. In particular, do not run notes-to-sermon fidelity audits unless the user explicitly asks to work on that separate project.

Articles must be generated by `backend.pipeline.matthew_exposition_authoring_runner`; Codex must not handwrite or silently patch reader-visible prose. Programmatic metadata normalization is allowed only when code proves reader-visible text is unchanged and records both manuscript SHAs.

Reviewer-call invariant: run one Independent Editorial Review for the initial draft, then exactly one Final Delta Review per revision. The Delta Review must return any next-round findings in the same response. Do not add a Score-Gap Review or send a revised manuscript through another full Editorial Review.

For Matthew exposition articles, a programmatically verified editorial review in which every applicable dimension reaches its own minimum in the quality profile (currently 80% of each dimension's weight) and no hard failure is declared, followed by a passing Program Audit with zero errors, triggers automatic Wang repository publication. There is no total-score threshold: `total_score` is reported for a reader and decides nothing, because one number let a weak dimension be carried by the others. The quality profile is the authority for the bars; do not restate a number here that the profile can change. The runner must create an `automated-publication-decision.v1` bound to the manuscript, editorial review, and audit SHAs; it must never label this as human approval. Publishing to the Wang repository is not deploying: do not deploy as part of this workflow.

# Operating the production machine

`docs/operations-runbook.md` is authoritative for deploying and for anything
touching the production machine. Read it before acting, not after something
looks wrong.

Three points it will save you from rediscovering. There is exactly one deploy
entry point, `scripts/deploy.sh`, run from the development checkout; anything
else you find that looks like a deploy script is either gone or does not deploy.
The directory named `smart-answer` is not the running code — releases live under
`smart-answer-deploy/releases/<sha>`. And a release venv must be built with the
interpreter pinned in `.python-version`, never with whatever `python3` your
shell resolves to, because this machine has three of them and one of them
produces a release that builds cleanly and then cannot start.

Every pull request declares its tickets with `Closes #N` before it merges.
GitHub will not create that link afterwards, and `scripts/deployed-issues.sh`
reports only real links, so a ticket connected after the fact is invisible.
