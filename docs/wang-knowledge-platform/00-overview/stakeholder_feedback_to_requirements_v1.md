# 同工反馈到产品需求与验收标准 v1

> **读者**：神学编辑
> **类型**：流程
> **状态**：当前
> **与代码对齐**：不适用
> **权威范围**：把同工反馈转成可验收需求的方法。不替代 Project Mission、共享知识模型或具体产品设计。

> 状态：首版需求基线。本文把教会同工的自然语言反馈转成可实现、可测试、可修订的产品需求；它不替代 Project Mission、共享知识模型或具体产品设计。

## 一、为什么需要这份文件

同工的反馈通常表达的是一种真实困难，但还不是可以直接交给程序实现的需求。例如：

> 我们都说教授讲得好，可是教授讲了什么、到底好在哪里，没人说得出来。

> 平常经常听教授讲因信成义，有没有人总结一下？

如果直接把这两句话翻译成“让 AI 写一篇摘要”，很容易得到一篇流畅却无法核查的文章。正确的转换过程是：

```mermaid
flowchart LR
    F["同工反馈"] --> P["辨认真实的使用者问题"]
    P --> O["定义读者需要获得的结果"]
    O --> K["确定所需知识与来源"]
    K --> R["写成系统需求"]
    R --> A["制定可观察的验收标准"]
    A --> V["用真实讲道验证"]
    V -->|发现缺口| K
```

因此，反馈不是需求本身；它是发现需求的入口。

## 二、把反馈写成 proper requirement 的格式

每项正式需求至少包含以下内容：

| 字段 | 要回答的问题 |
| --- | --- |
| 需求 ID | 以后讨论、实现和测试时如何稳定引用？ |
| 使用者 | 谁遇到这个问题？ |
| 使用情境 | 他在什么情况下需要这项能力？ |
| 期望结果 | 完成后，使用者能够理解或完成什么？ |
| 系统行为 | 系统必须提供什么，而不是只说“用 AI 做”？ |
| 来源与归属 | 哪些内容是教授明说、直接推论、编辑综合或待研究？ |
| 验收标准 | 我们如何客观判断它是否合格？ |
| 非目标 | 这一阶段明确不做什么？ |

可以使用下面的句型：

> 作为一位 ______，当我 ______ 时，我需要 ______，使我能够 ______。系统必须 ______；只有在 ______ 时，才算通过验收。

“做一个漂亮的总结”“请 AI 写因信成义”“建立思想库”都不是完整需求，因为它们没有说明读者获得什么、内容依据什么，以及怎样才算正确。

## 三、从第一条反馈得到的需求

### 原始反馈

> 我们都说教授讲得好，可是教授讲什么了，到底好在哪里，没人说得出来。

### 使用者问题

长期听众记得教授“讲得好”，却难以用普通语言复述：

1. 教授反复主张什么；
2. 他凭什么得到这些结论；
3. 他怎样解释经文、原文、文体、历史与上下文；
4. 这些讲法为什么值得注意；
5. 这些总结可以回到哪些原始讲道核对。

“好在哪里”不是要求系统赞美教授，而是要求系统把抽象评价转成可观察的特征，例如：问题是否说清楚、证据如何使用、推论是否完整、如何处理原文与译本、不同讲道之间是否形成稳定的方法。

### 正式需求

#### REQ-THOUGHT-OVERVIEW-001：教授讲了什么

系统必须让非专业读者看见教授跨越多篇讲道反复出现的核心主张，而不是只列讲道标题或生成单篇摘要。

验收标准：

- 每条“反复出现”的思想至少显示所覆盖的讲道范围；只有单一来源时必须明确标示。
- 每条思想用普通中文说明，并可展开查看教授原话、经文、论证步骤和精确来源。
- 系统区分教授明说、由论证直接推出、编辑跨讲综合及尚待研究的内容。
- 新讲道加入后，既有思想可以得到支持、扩展、限制、对照或修正，而不是复制成另一条近义标题。

#### REQ-METHOD-EXPLANATION-001：教授好在哪里

系统必须用可核查的例子说明教授经常采用的释经方法和论证习惯，不以“深刻”“精彩”“很有亮光”等评价代替分析。

验收标准：

- 每项方法说明都包含“他做了什么”“为什么这样做”“在哪些讲道中出现”。
- 原文、译本、文体、上下文、历史背景和逻辑推论分别记录，不能压缩成模糊的“重视解经”。
- 若同一方法在不同讲道中的使用有张力或变化，系统必须保留差异。
- 读者能够从总结进入相关释经、专题、问答或原始讲道。

## 四、从第二条反馈得到的需求

### 原始反馈

> 平常经常听教授讲因信成义，有没有人总结一下？

### 使用者问题

听众知道这是教授反复谈论的主题，却缺少一篇能够回答下列问题的综合说明：

- 教授所说的“义”是什么？
- 为什么教授强调“因信成义”，而不愿只说“因信称义”？
- “信”在论证中是什么角色？
- 义、信、恩典、律法、约、悔改与顺服如何连接？
- 这些解释分别来自哪些讲道和经文？

### 正式需求

#### REQ-TOPIC-SYNTHESIS-001：跨讲道专题综合

系统必须能够从全库相关讲道中形成一个专题的主张网络和可读论述，不能把人工先选出的几篇讲道误当作全部材料。

验收标准：

- 专题显示当前检索范围、已详细整理的来源和尚未纳入的候选来源。
- 内容按问题和论证组织，而不是按讲道日期依次拼接。
- 重复主张合并呈现；补充、限制、反对和时间变化保留为关系。
- 与专题无关或证据不足的材料允许不归组，不能为了达到百分之百覆盖而强塞。

#### REQ-RIGHTEOUSNESS-001：“因信成义”必须成为可见子专题

现有上位主题“义、信与人神关系”可以保留，但系统必须把“因信成义及其与因信称义的区别”呈现为读者可直接找到的子专题或独立篇章，不得埋在宽泛分类中。

验收标准：

- 标题、导航或目录中可以直接找到“因信成义”。
- 正文有独立小节说明“成义／称义”的用词与论证，不只在搜索标签中出现。
- 至少回答“教授的结论是什么、理由是什么、引用哪些经文、与他反对的理解有何区别”。
- 采用教授实际用语。模型不得因通行神学术语而自动把“成义”改写为“称义”。
- 每个关键结论都能展开到多篇讲道中的原话或精确来源；证据不足处必须明确说明。

#### REQ-TERMINOLOGY-FIDELITY-001：关键术语忠实性

系统必须把教授反复强调或主动修正的术语视为高风险语义，生成与审核流程不得静默正规化。

验收标准：

- 关键术语保存原词、上下文、来源和可追踪的修订记录。
- AI 若改变关键术语，必须提供可逐字核对的来源依据，否则修正不得进入候选知识。
- “教授的术语”“编辑为读者所加的解释”和“独立事实或神学核查”分别标示。

## 五、两条反馈共同产生的基础需求

#### REQ-ARGUMENT-TRACE-001：不只给结论，也保存论证

读者看到的重要结论必须可以沿着论证关系回到理由、经文、观察、反方立场和原始来源。论证层是内部知识基础；读者界面显示的是清楚解释，不是内部 ID 或原始图结构。

#### REQ-READABILITY-001：知识图必须经过篇章编排

共享知识图不能直接当作文章。每项释经、专题、问答或微讲道必须有独立的篇章编排计划，决定先回答什么、哪些内容展开、哪些只作链接、哪些暂缓，并记录这些属于编辑判断。

#### REQ-SCOPE-DISCLOSURE-001：诚实说明语料范围

局部验证可以先交付，但必须区分“目前五篇讲道支持的结论”与“教授全部两百多篇讲道的完整立场”。尚未处理不得写成教授没有讲过。

#### REQ-READER-ANSWER-001：同时提供简明回答与完整说明

面向读者的问答或专题入口应先提供可以立即理解的简明结论，再提供完整论证、限制和来源。简明回答不能成为唯一内容，内部审核资料也不能直接暴露给普通读者。

## 六、第一轮需求验证：罗马书五篇讲道

为验证上述需求，首轮选取五篇与罗马书、义和信直接相关的讲道，建立中立研究批次 `RB-RIGHTEOUSNESS-FAITH-ROMANS-VALIDATION-01`。该批次是需求验证切片，不代表已穷尽全库相关材料。

机械验收结果：

- 5 篇讲道、388 个来源片段、89 条候选主张、212 个证据步骤；
- 形成 111 条已整合主张关系，其中 46 条为经双模型接受的跨讲关系；
- 产生 4 个释经候选和 5 个专题候选；
- 89 条主张中 88 条获得明确产品去向，1 条一般生活应用保留为未归组，没有强行塞入“因信成义”；
- 两条间接 `extends` 关系存在模型分歧，已排除，不阻挡其余候选；
- 成功发现一处 AI 把教授“被成为义”改写成“被神称义”的术语失真，并建立可核查的来源忠实性修正规则。

这轮验证证明共享知识模型可以识别专题骨架，也证明“术语忠实性”必须成为正式要求。它还没有证明读者会认为最终文章清楚好读，因为专题文章和使用者测试尚未完成。

## 七、这轮怎样才算真正完成

首个面向读者的验收成果应是一篇候选专题，例如：

> 王守仁教授所讲的因信成义：义、信与人神关系

它至少应包含：

1. 一段普通读者能懂的简明回答；
2. 教授关于义、信和人神关系的核心主张；
3. “因信成义”与“因信称义”的独立说明；
4. 经文、原文或语义论证；
5. 恩典、律法、悔改与顺服的关系；
6. 教授反对或修正的理解；
7. 多篇讲道的精确来源与原声定位；
8. 语料范围、证据薄弱处和编辑综合的明确标示。

验收时不只问“文章写得好不好”，而要请同工完成三个任务：

- 用自己的话回答“教授所说的因信成义是什么”；
- 指出教授为什么这样主张；
- 从文章进入一处原始讲道，核对该结论。

三项都能完成，才说明同工的原始反馈真正得到解决。

## 八、本阶段非目标

- 不判断教授的神学立场最终是否正确；独立事实核查与神学评论是后续阶段。
- 不因为形成了候选结构就自动发布专题文章。
- 不要求先人工审核全部两百多篇讲道才开始局部交付。
- 不把手工文章、AI 摘要或研究批次名称直接当成 canonical topic。
- 不让某一个产品拥有私有的主张、术语或来源体系。

## 九、以后处理新 feedback 的规则

每条新反馈进入 backlog 前，必须先回答：

1. 这是使用者问题、内容错误、流程问题，还是界面建议？
2. 它影响共享知识、篇章编排，还是某个产品投影？
3. 是否需要新数据对象，还是现有对象已经足够？
4. 哪些结果可以由程序机械验证？
5. 哪些判断必须由独立 AI 或同工审核？
6. 什么证据出现时，我们会承认当前设计失败并修改上游？

只有回答完这些问题，feedback 才成为 proper requirement。
