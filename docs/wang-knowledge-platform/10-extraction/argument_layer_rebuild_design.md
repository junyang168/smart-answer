## 零、先有評測，再寫代碼

**負責人 2026-11-16：記住評測先行；試作裡花了很多時間的設計規則和案例要帶進正式做法；請幾位同工一起審閱，建 golden case library。** 這一節先於其他各節實作：沒有評測就不換模型、不改 prompt、不重建任何一講。

### 0.1 庫裡有什麼

| 層 | 內容 | 現在有的 |
| --- | --- | --- |
| 規則 | 每條設計規則一句話，連同它從哪個負責人裁定或試作經驗來 | [creation 設計 3.2](./claim_creation_flash_design.md)、[試作經驗](./argument_layer_poc_lessons_20261116.md) 十二條 |
| 案例 | 一講的標準答案：分組、Claim 提綱、分步、每句落腳處、題外話、投影片案例 | 太5 第 1 講五組分步答案（`backend/pipeline/argument_golden/`）；投影片 13 條（`chapter_slide_cases.json`） |
| 評分 | 程式把一次生成的結果與案例比對，報出拆錯、併錯、漏、多出 | 試作的評分腳本（只在暫存目錄，要轉正式） |

**每條規則至少對應一個案例**，案例能讓違反規則的結果不及格。只寫在 prompt 裡、沒有案例的規則，等於沒有檢查（試作經驗第 10 條）。

### 0.2 案例的狀態

試作的五組答案大多是 Claude 草擬、負責人改過其中幾處，不能直接當標準。每個案例的每一條答案都有狀態：

| 狀態 | 意思 | 用來評分嗎 |
| --- | --- | --- |
| 草擬 | Claude 或模型寫的 | 不用 |
| 同工審閱中 | 3–5 位同工（負責人 2026-11-16）用現有編輯角色登入，各自獨立作答，彼此看不到 | 不用 |
| 定案 | 至少 3 人作答且多數一致（少數意見照記）；沒有多數時由負責人裁定，記下理由 | 用 |

**負責人已經裁定過的直接定案**，例如 G02 的兩次對照分成兩步（2026-11-16）。

**已知的衝突要先處理**：G02 草擬答案把心臟幻燈片故事當成一步 Evidence，與負責人 2026-11-16 的題外話裁定相反。這一條改成題外話，再交同工審。

**答案用穩定的句子位置**（段落 ID 加句序），不用試作裡每組請求自己的編號（#1、#2…），否則原文一動就對不上。

### 0.3 同工怎麼審

審閱的同工不熟電腦也不熟 AI，原則與[題外話審閱頁](../20-knowledge/knowledge_instance_and_asides_solution.md#五同工的審閱介面)相同：一次一個問題、能聽原聲、黃色標示原文、兩三個大按鈕、不出現 ID 和術語。

問題用白話，一次只問一件事，例如：

- 「這幾句（黃色標示的）是在講同一個理由嗎？」 是／不是，分成兩段
- 「教授講這一段，是要說明哪一點？」 從列出的兩三個要點選一個，或「都不是」
- 「這一段在講經文，還是題外話？」

**各自作答，不看別人的答案。** 兩人一致就定案；不一致就連同兩個答案交給負責人。同工答案與負責人裁定都存在新知識庫實例，有版本歷史，記下誰、何時答的。

### 0.3.1 審閱進入流程（負責人 2026-11-16）

**負責人：「把同工審閱放進流程，做一個容易用的介面讓我們審閱和批准；同工可能只說他的看法，你要準備好再問清楚。」**

流程裡每一講的順序：

1. **出題**：程式從案例裡挑出要審的答案：草擬的答案，以及生成結果與答案不一致的地方。每一條變成一道白話題目，附原聲範圍、原文、兩三個選項。
2. **作答**：3–5 位同工用現有編輯帳號登入，各自作答。可以選一個選項，也可以只寫自己的看法。
3. **追問**：只寫了看法、或看法與所選選項不一致時，模型讀他的話，決定兩件事之一：看法已清楚對應某個選項，就記下並請他確認；不清楚，就提一個具體的追問（例：「你是說這三句是一個理由，還是說第三句是結論？」）。追問出現在他下一次打開的頁面頂端。一題最多追問兩次；兩次後仍不清楚，原話照記，算「意見未定」，交負責人。
4. **定案**：至少 3 人有明確答案、多數一致，就定案；少數意見照記。沒有多數或有「意見未定」的，進負責人的待裁定清單。負責人在同一頁裁定，寫一句理由。
5. **回寫**：定案答案寫回 golden cases（`cases.json`，經 PR），評分才用到它。審閱的原始記錄（誰、何時、原話、追問與回答）留在新知識庫實例。

**記錄放在哪裡**：新知識庫實例（`smart_answer_knowledge_v2`）的 `argument_review` schema，三張表：題目、作答（含原話）、追問與回答。不放在現有正式庫。

**頁面**：`/admin/argument-review`（在 /admin 首頁）。同工只看到「下一題」：原聲播放鍵（範圍前後各兩句）、原文（範圍以黃色標示）、題目、選項大按鈕、「我想說說我的看法」文字框、進度。追問排在最前面。負責人另有「待裁定」與「全部題目」兩個分頁。頁面不出現 ID、句號、英文術語。

### 0.4 怎麼評分

只用定案的答案。每條答案與生成結果按句子比對：

| 答案 | 生成結果 | 判定 |
| --- | --- | --- |
| 一步 | 恰好一筆記錄蓋住這一步的句子（或任一接受的變體） | 對 |
| 一步 | 兩筆以上記錄分這一步 | 拆錯 |
| 兩步 | 一筆記錄同時蓋住兩步 | 併錯（`accept_merge` 允許的除外） |
| 一步 | 沒有記錄 | 漏 |
| — | 一筆記錄只蓋到題外話或「其他」 | 多出 |
| Claim 本身的話 | 這些句子是那條 Claim 的 SourceFragment | 對；否則漏 |
| 題外話 | 這些句子不在任何 Evidence 裡 | 對；否則錯 |

例：G02 的 c1（#21–28）和 c2（#29–35）是兩步。生成結果若用一筆 Evidence 蓋住 #21–35，判併錯。

報告列出每條錯誤：組、答案、生成的記錄、原文。停下的條件見第八節。

### 0.5 怎麼用

1. **改 prompt 之前先加案例。** 新發現的問題先寫成案例並定案，再改 prompt；改前改後兩版都對全庫評分，不只對新案例。
2. **換模型之前先評分。** GPT 6.1 sol 正式生成前，先對第 1 講的定案答案評分（見第八節）。
3. **每講重建前先凍結那一講的答案。** 沒有同工案例時，由 Claude 在任何 GPT 答覆出現前讀完逐字稿寫下答案並提交（`argument_golden/<講>/reading-before-run.md`），作為保留測試。第一次評分就是保留分數，之後不改；發現是答案錯了，另記更正與理由，兩個分數都報。
4. **評分報告**列出每條不及格的答案、對應的規則和原文，交負責人。

## 一、流程

一講分六步。前四步生成，第五步驗證並入庫，第六步給按章頁面用。

| 步 | 誰做 | 做什麼 | 程式核對 |
| --- | --- | --- | --- |
| 1. 分組 | 模型 | 一組是一個論證：一個主要結論，加上為建立它所講的全部內容 | 每段恰好歸一組 |
| 2. Claim 提綱 | 模型 | 每組一個上層結論，下面是他逐一講出的部分 | 範圍落在原文上 |
| 3. 分步 | 模型 | 把每句放進一步論證（理由、對照、故事、反方、問題）、某條 Claim 本身的話、其他，或題外話；把清單上不是 Claim 的條目退回 | 每句恰好一次；一行一個「↔」或一個「因為」；每條留下的 Claim 至少有一步；他明確引用經文的句子不在其他或題外話裡；退回的條目合規 |
| 4. 建記錄 | 模型＋程式 | 模型只定每一步的類型、寫 statement 和他說出的經文；程式切 SourceFragment、生成連結 | 每一步一筆記錄；每句都有落腳處 |
| 5. 驗證入庫 | Flash | 原文與經文引用、Evidence、Claim 三層自下而上檢查與修正；每講一次交易寫入新實例並回讀 | 見第三節 |
| 6. 投影片 | 模型＋程式 | 從新實例讀出本講提綱，生成按章投影片 | 時間、對齊、經文、負責人案例 |

**每句都有落腳處。** 第 3 步的三種歸屬在第 4 步各有去處：論證步驟成為 Evidence、Observation 或 Position；「Claim 本身的話」成為那條 Claim 的 SourceFragment；「其他」（轉場、口頭語）以理由排除。凡是「重複」的排除，都要指名保存它的記錄，程式核實。這條來自試作第 7 條經驗。

**經文清單在分步之前生成。** 程式先用現有的經文引用工具列出他明確引用經文的句子，連同經文交給第 3 步；這些句子必須留在論證裡（論據、問題、反方或 Claim 本身的話），不能放進其他或題外話（負責人 2026-11-16：一次做對，不靠事後補）。

**問題與反方。** 他提出、留到後面才回答的問題是 Question，不是 Claim；當場自問自答的是一步論據；他提出再駁斥的別人看法是 Position，連同他順口的評語。

**題外話**：他批評別人卻沒有給經文或推理，或用來襯托這種評論的個人故事。說出對方為什麼錯（動機、身份）不算依據。用來支持一個觀點的故事整段是一步，結尾即使在稱讚他也不切出來（負責人 2026-11-16）。題外話只是提案，由同工批准。

**退回不是 Claim 的條目。** 第 2 步的 Claim 提綱寫在逐句閱讀之前，可能把論據或題外話列成 Claim。第 3 步可以把這樣的條目退回：`evidence`（用來證明另一條 Claim 的經文讀法、律例的目的或出處、另一位使徒的規定、定義、故事裡別人說的話）、`restates`（重述同組另一條）、`digression`（題外話）。他為這一條本身給了理由的（原文字義、另一處經文），仍是 Claim。程式核對後移除該條，記在 `not-claims.json`；只能退回本組新列、別組沒有沿用的條目。

## 三、驗證直接在新實例上做

**現在**：Flash 驗證候選時開一個一次性的私有 PostgreSQL，用完停止；結果不進任何長期保存的庫。這是為了保護正式庫：未經驗證的候選不能碰正式資料。

**改為**：新實例在切換前不是正式庫，所以 Flash 直接在新實例上驗證。

1. 一講的候選以一個 ChangeSet 載入新實例，狀態為 candidate。
2. 新實例裡已有這一講時，舊記錄在同一個 ChangeSet 裡退役，不直接覆寫；版本歷史保留舊的。
3. Flash 照現有分層在新實例上檢查與修正，每次修改是一次短交易，寫完回讀。
4. 中途停止時，從新實例裡已提交的事實接續，不換目錄重跑。

**保留的保護**：重建工具只接受 `ARGUMENT_DATABASE_URL`；它拒絕現有正式庫的位址（第二節）。一次性私有庫的入口保留給其他還在用它的流程，不刪。

## 四、運行記錄放哪裡

架構規定模型的原始材料與答覆存成 JSON 檔案，資料庫存已提交的事實。試作把這些檔案放在工作階段的暫存目錄，這在正式做法裡不允許。

| 項目 | 規定 |
| --- | --- |
| 位置 | `ARGUMENT_RUN_ROOT`，預設為資料目錄旁的 `argument-layer-runs/`（`/opt/homebrew/var/www/church/web/argument-layer-runs/`），每講一個子目錄 |
| 內容 | 每次模型請求、原始答覆、程式編譯結果、核對報告、退回原因 |
| 不可放 | 工作階段暫存目錄；程式發現路徑在暫存目錄下就拒絕執行 |
| 與資料庫的關係 | 新實例的 ChangeSet 記下它來自哪個運行目錄與哪些答覆的 SHA |

## 五、重放

**修程式後重算，不重新調用模型。** 試作中多次證明這是查證修正的最快方法：謙卑那條修正後，重放已存答案，Claim 就多了那段原文，零模型調用。

- 重放是正式的指令：指定一講的運行目錄，程式用已存的答覆從第 1 步重走到第 4 步，再進第 5 步。
- 輸入（原文、prompt、schema）與已存答覆綁定的版本不同時，重放停在那一步並說明，不偷用舊答覆。
- 重放只在工程修正時用。內容問題要重新調用模型，依現行預算與審閱規則。

## 六、投影片讀新實例

現在按章投影片從生成目錄的檔案編出提綱（`--creation-run`）。改為從新實例讀：

- 本講的 Claim、它的 Evidence 步驟與經文、Claim 本身的原文段落、反方，全部從新實例按來源讀出。
- 讀出的內容與現在的提綱格式相同，投影片的其餘部分不改。
- 提綱帶上新實例的版本（ChangeSet），投影片記錄它是從哪一版論證層生成的；論證層變了，舊投影片標為需要重做。

## 七、試作代碼怎麼轉正式

| 部分 | 現在 | 處理 |
| --- | --- | --- |
| 分步生成（`--steps-first`） | #702 分支，標為實驗 | 成為唯一的生成方式；去掉「實驗」標記，加進重建指令 |
| 其他生成模式（`--single-pass`、未分步的整組模式） | 試驗用 | 重建指令不提供；切換後與舊實例一起刪除 |
| 試作的代答驅動檔（`drive.py`，寫死 Claim） | 暫存目錄 | 刪除；由第五節的重放指令取代 |
| 生成模型 | 試作由 Claude 代答 | GPT 6.1 sol，medium，經 Codex 訂閱（負責人 2026-11-16）；品質按第八節監控 |
| 驗證 | 一次性私有庫 | 新實例（第三節） |
| 運行目錄 | 暫存目錄 | `ARGUMENT_RUN_ROOT`（第四節） |
| 投影片提綱 | 讀生成目錄 | 讀新實例（第六節） |
| 負責人案例 | `chapter_slide_cases.json` | 保留；新問題先加案例 |

**新的重建指令**一次做一講：讀原文、跑第 1–5 步、寫入新實例、報告結果。它不提供改寫正式庫的選項。

**#702 分支先合併**。分步生成與試作中的修正都在它上面；新代碼在它之上做，不另開平行版本。

## 八、生成品質監控

**生成模型是 GPT 6.1 sol，medium，經 Codex 訂閱（負責人 2026-11-16）。** 試作的 prompt 是在 Claude 代答下調好的，所以不能假定 GPT 一樣好；每一講都要評分，負責人要求密切監控。

**一講做完，才做下一講（負責人 2026-11-16）。** 保留評分之後，同一講繼續改、繼續跑，直到通過；下一講不跑、不重放、不修它的問題。GPT 的第一次正式作答先按第 1 講的定案答案評分（第零節）；答案還沒定案的部分，先由同工審完。

**一輪改完已知的問題再跑（負責人 2026-11-16）。** 評分後把所有已知原因一起改，只跑一輪，不一個問題跑一輪。

**Claim 提綱的寫法**。蓋子只寫本組那一個結論，不重述下面各條；一段推理的前提與中間環節是論據，只有另有論據、能單獨回答一個問題的判斷才另立一條。

| 評什麼 | 怎麼算 | 停下的條件 |
| --- | --- | --- |
| 分組 | 與凍結答案的分組比，逐段 | 一個問題與回答它的段落分在兩組，且回答沒有連回問題 |
| 主要結論 | 每組對、部分對、錯 | 任何一組錯 |
| 分步 | 與答案比：拆錯、併錯、漏、多出 | 多出（他沒講的步驟）任何一處；其餘合計超過答案步數的一成 |
| 每句落腳處 | 程式核對：每句恰好一次、「重複」都指名保存的記錄 | 任何一句沒有落腳處 |
| 經文 | 他念出的經文都在 SourceFragment 裡；沒有他沒講的經文 | 任何一處多出的經文 |
| 投影片 | 程式核對與負責人案例 | 任何一條案例不過 |
| 退回 | 每一步被程式退回的次數與原因 | 同一原因在兩組以上出現：先找共同原因 |

**停下時**：不換 prompt 重跑來湊分數。把評分表、退回原因和 GPT 的原始答覆交給負責人；要改 prompt 時，照試作經驗第 1 條，用同一份答案評前後兩版。

**每一講怎麼評（負責人 2026-11-16：不能每講都靠人工案例）。** 人工案例只用來校準評審，不用來評每一講。每講生成後分三層：

1. **程式核對**（硬性，不調模型）：每句恰好一次；他引用的經文都在論證裡；每條留下的 Claim 有支持它的一步；退回的條目合規。任何一條不過，這一講不往下走。
2. **獨立評審**（調模型，用與生成不同的模型，Claude 訂閱 CLI）。評審讀逐字稿與 GPT 的結果，一條一條回答窄問題，不給整講打分：
   - 每條 Claim：他自己有沒有說出這個判斷（引原句）？還是用來證明另一條的論據、別人的話，或從故事推出而他沒說的？
   - 每條題外話：他有沒有給經文或推理？
   - 每個 Question：他有沒有回答、在哪裡？
   - 每個 Position：是不是別人的看法、他有沒有駁斥？

   評審只交回它與 GPT 不同的條目，每條附原句與依據的規則。
3. **審閱頁**：每條不同之處變成一道題，附評審提出的答案，由負責人或同工裁定。負責人只裁定不同之處，不審整講。

**評審自己也要評**。在有人工案例的第 1、2 講上跑評審，比對它的判斷與負責人的定案：命中多少、漏掉多少。評審的 prompt 改了就重評。每講另抽幾條評審同意的條目給負責人裁定，查它漏掉的。

投影片照按章頁面流程交負責人試聽；負責人指出的問題先加進案例，再修。

**每講記帳**：模型調用次數、輸入／輸出 token、生成與驗證各自的時間、退回輪數。記在運行目錄，報告裡列出。

## 九、驗收

1. 新實例建立；重建工具指向現有正式庫時拒絕執行。
2. 太5 第 1 講用已存答覆重放進新實例，零模型調用；讀出的 Claim、Evidence、SourceFragment 與試作檔案一致。
3. 從新實例生成的按章投影片通過全部程式核對與負責人案例。
4. 中途停止後接續，不重複寫入、不重複調用。
5. GPT 對太5 第 1 講作答，按第八節評分，結果交負責人。
6. 現有正式庫與正式網站在整個過程中不受影響。
