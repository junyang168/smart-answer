# 論證形態評測集

> **讀者**：Solution architect、Developer。
> **類型**：規範。
> **狀態**：當前。
> **與代碼對齊**：未核對（尚未實作）。
> **權威範圍**：生成論證層的 prompt 改動怎麼驗證：評測集收什麼、案例怎麼寫、怎麼評、怎麼增長。每講怎麼評見 [論證層重建設計](./argument_layer_rebuild_design.md) 第八節。

## 一、為什麼

2026-11-16 第 2 講改了六輪 prompt。每輪都重跑整講（16–25 次 GPT 調用、15–20 分鐘），也都重跑第 1 講的兩組來查有沒有改壞。這樣有三個問題：

- **貴**。每改一句 prompt 就要整講重跑，負責人：「we can't afford doing this every time we change a prompt」。
- **看不清**。第 4–6 輪得分 32、32、31，錯的地方每輪換位置；整講的分數大半是 GPT 每次不同，不是 prompt 的效果。
- **漏查**。只重跑第 1 講兩組，其他形態有沒有被改壞，沒人知道。第 4 輪加的「推理鏈只寫結論」就把第 1 講 G03 的首尾呼應併掉了，是碰巧查到的。

所以 prompt 改動不再拿整講驗證，而是拿一組短案例：每條案例是他論證的一種**形態**，帶負責人的裁定，程式能判對錯。整講只在跑新的一講時才跑。

## 二、案例是什麼

一條案例是一講裡的一小段（通常一組或其中幾分鐘），只考一種形態，例如「他講的故事用來支持一條 Claim，結尾稱讚他的話仍屬故事」。

每條案例記：

| 欄位 | 內容 |
| --- | --- |
| 形態 | 屬哪一種（見第三節） |
| 出處 | 哪一講、哪幾句（逐字稿原文定位，不靠句子編號） |
| 裁定 | 負責人的定案，及其出處（審閱頁題目、對話日期） |
| 檢查 | 程式能判的幾條斷言，見下 |
| 用途 | `train`（可以看著它改 prompt）或 `held_out`（不看，只評） |

**檢查是斷言，不是標準答案全文。** 一條案例不要求 GPT 的結果與某份提綱逐字相同，只查這種形態有沒有判對：

- 某句在某條 Claim 的論據裡（或：在題外話裡、在某個 Question 裡、在某個 Position 裡）；
- 某段話**沒有**成為 Claim（例：「把經文講清楚能幫助人得到釋放」）；
- 某兩段話在**同一條**／**不同的** Claim 裡（查拆分與合併）；
- 某個 Question 在本段**沒有**被回答；
- 沒有 Claim 的文字含「教授」或故事裡的人。

斷言用他的原話定位，所以換了分組或句子編號，案例仍然能評。

## 三、形態清單（起始）

取自第 1、2 講負責人已有的裁定。

| 形態 | 裁定 | 例子 |
| --- | --- | --- |
| 故事作論據，結尾屬故事 | 故事整個一步，不按情節拆；結尾稱讚他的話仍屬故事 | 工程師的故事 |
| 他沒說出的教訓 | 從故事推出、他自己沒說的，不立 Claim | 「把經文講清楚能得釋放」 |
| 沒有根據的批評 | 題外話，不是論據 | Time Magazine；學者眼瞎 |
| 他駁斥的看法 | Position，`supports` 寫駁它的 Claim | 「十條誡要守」；挪亞禁血 |
| 留到後面回答的問題 | Question，本段不回答 | 太五27–28 |
| 當場回答的問題 | 是一步論據 | 使徒行傳十五章與林前八章 |
| 經文讀法作論據 | 是論據，不立 Claim | 以弗所書四13；利未記十七、十八章作出處 |
| 他另給理由的讀法 | 是 Claim | 羅馬書八4 δικαίωμα；使徒行傳十五章的姦淫 |
| 推理鏈 | 前提與中間環節是論據，只寫結論 | 禁血；主觀／一個意思／找證據 |
| 他當作教導講的前提 | 是 Claim | 「認識之後必有回應」 |
| 蓋子與各部分 | 蓋子只寫合起來的結論；各部分有自己論據的各成一條 | 第 1 講 G03 首尾呼應 |
| Claim 的寫法 | 直接寫他的判斷，不寫「教授認為」或故事裡的人 | 「那位弟兄求……教授判斷神不會聽」 |
| 只有題外話的一組 | 一組可以沒有 Claim | Time Magazine 單獨一組 |

每種形態最多三條案例。新的例子只在它讓現有三條都過、自己卻不過時才加入，否則替掉三條中最弱的一條。

## 四、怎麼跑

- **只跑改動碰到的那一步。** 案例存的是那一步的完整輸入（從已有運行存下的答覆裡取，不重跑上游）。改 Claims prompt 只跑 Claims 那一次調用；改逐句 prompt 只跑逐句和記錄兩次。
- **並行。** 案例互不依賴，一起跑；三十條案例幾分鐘內評完。
- **評分由程式做**：每條斷言過或不過，按形態列出。分數不是一個總數，是每種形態過了幾條。
- **train 與 held_out 分開報。** 改 prompt 時看 train；held_out 只在定稿時看一次，不拿它調。held_out 取自第 3 講以後的講，第 1、2 講的案例都是 train。

一次 prompt 改動算通過：所有 train 案例都過，held_out 沒有比上次少過。一條不過，先問是 prompt 的問題還是案例的裁定不清；裁定不清的，上審閱頁問負責人。

## 五、怎麼增長

評測集隨每一講增長：

1. 跑新的一講（整講，唯一要整講跑的時候）。
2. 程式核對、Gemini 評審和審閱頁找出問題；負責人裁定。
3. 一條裁定若沒有現有形態涵蓋，成為新形態的第一條案例；若屬現有形態而現有案例都過了，按第三節的上限決定是否加入。
4. 改 prompt，直到整個評測集——舊案例和新案例——都過。
5. 這一講自己剩下的錯，在審閱頁裁定後直接改它的論證層，不再為它重跑 GPT。

這樣評測集記下了到目前為止遇過的每一種論證方式，一次 prompt 修正不會悄悄改壞之前的形態。

## 六、與 Gemini 評審的關係

評審和評測集各管一件事：評審在**每一講**上找 GPT 可能錯的地方，交給負責人；評測集在**每次改 prompt** 時查形態有沒有被改壞。評審的 prompt 也拿評測集評：同一組案例，看評審判得和負責人一樣的有幾條。
