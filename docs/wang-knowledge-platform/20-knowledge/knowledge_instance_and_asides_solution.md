## 一、起因

2026-11-16 負責人審閱《2011 NYSC 專題：馬太福音釋經（二）1》的按章頁面，指出兩件事。

**論證層只存在檔案裡。** 這一講的 Claim 與 Evidence（五組）是試作，只存在一次工作階段的暫存目錄。一次清理就會全部消失，也沒有地方記錄編輯的審閱決定。

**題外話被當成論證。** 約 S0255–S0292，他先說「今天有一些學者，看聖經眼睛都瞎了」，接著講兒子在醫學院用心臟幻燈片準備考試的故事（約三分半鐘）。模型把這兩段建成 Evidence，支持「耶穌明講祂是神」那條 Claim；按章頁面因此給了一整張投影片。負責人的判斷：「整段都跟釋經沒有太大關係，有點 self promotion」；並且「教授明顯在攻擊其他學者，而又沒有有利證據，只是 comment 的話，最好都 mark」。

## 二、新知識庫實例

**決定（負責人 2026-11-16）：** Claim 層寫入一個新的 PostgreSQL 實例，schema 與現有 `wang_knowledge` 相同。一切順利的話，新實例取代現有實例。

**為什麼可以乾淨重建：** 目前沒有真實讀者在使用知識庫。文章、CVP、問答指向舊 Claim ID 的部分，不需要相容或 ID 對照；重建後由新實例重新產生。

| 項目 | 做法 |
| --- | --- |
| 位置 | 同一台 PostgreSQL 伺服器上的新資料庫（暫名 `smart_answer_knowledge_v2`），用 `store.migrate()` 建立同一 schema |
| 寫入 | 照現有規範：短 transaction、ChangeSet、版本歷史、提交後回讀 |
| 誰讀它 | 切換前只有開發用的卡片伺服器（例如 3637）讀它；正式網站仍讀舊實例 |
| 備份 | 納入現有資料庫備份 |
| 切換 | 把 `KNOWLEDGE_DATABASE_URL` 指向新實例並部署；舊實例保留唯讀一段時間以便回退，之後退役 |

**切換條件**（全部滿足才切換）：

1. 馬太福音第五章各講在新實例重建完成，Claim 與 Evidence 經過現行審閱流程。
2. 按章頁面（投影片、播放）只讀新實例即可完整運作。
3. 至少一篇文章與一組固定問答題，在新實例上產生並通過現行審核。

## 三、題外話的判準

**判準是他有沒有給依據，不是他有沒有批評人。** 標記只記錄「這段有沒有在論證」，從不判斷他說得對不對。

兩類要標：

1. **無依據的評論**：批評學者或其他讀經的人，卻沒有給經文或推理支持，只是評論。
2. **個人插曲**：講他自己的經歷或故事，用來襯托上面那種評論，而不是解釋某節經文。

太5 第一講的例子：

| 他說的 | 有依據嗎 | 標不標 |
| --- | --- | --- |
| 「很多人……解經啊，完全搞錯」（S0071），把哀慟得安慰解成一般的安慰 | 有：inclusio 顯示各福都是天國的祝福 | 不標，這是反方與他的回答 |
| 「今天有一些學者，看聖經眼睛都瞎了」（S0255 起） | 沒有 | 標 |
| 兒子的心臟幻燈片故事（S0260–S0292） | 襯托上一段的評論 | 標 |
| 「有些人說耶穌從來沒有說祂就是神，我說哪裡沒有？一大堆！」（S0293 起） | 有：前面的太5:11–12，後面猶太人對彌賽亞的觀念 | 不標 |

## 四、標記與審閱

**題外話是論證層的一種新記錄**，存在新實例裡，與 Claim、Evidence 並列：

| 欄位 | 內容 |
| --- | --- |
| 來源與範圍 | 哪一講、從哪一句到哪一句，連同原文片段（SourceFragment） |
| 類別 | 無依據的評論，或個人插曲 |
| 理由 | 一句具體說明，例如「批評學者看經眼瞎，沒有給經文或推理」 |
| 審閱狀態 | 提議 → 批准或駁回；記下誰、何時、根據哪一版原文 |

**流程沿用 D4 的四步，只是最後一步一定由人做：**

1. **提議**：建 Claim 時，模型照第三節的判準提出題外話範圍。它不再把這些句子建成 Evidence。
2. **程序核對**：範圍落在原文上、沒有和 Claim 本身的原文重疊、每一句都有歸屬。
3. **模型複核**：另一個模型照同一判準獨立檢查，指出該標未標或不該標的。
4. **編輯批准**：編輯看原文與理由，逐條批准或駁回。這一步不能省，因為「有沒有在論證」正是這裡要下的判斷。

**只有批准的標記生效。** 原文不刪；被標的句子仍在逐字稿與知識庫裡，只是不再被當成論證。來源或原文版本變了，舊的批准不沿用，要重新審。

**已有的類似機制。** 逐句記錄裡的排除理由已有 `background_only`，定義為「必須有人批准才算數」。題外話記錄採用同樣的原則，但範圍更具體，也能被頁面讀到。

## 五、投影片與播放

**投影片**

- 批准的題外話範圍不生成投影片，也不生成要點。
- 投影片的程序核對（要點時間、論證對齊、念經文時要顯示、負責人案例）都略過這些句子。
- 前一條要點一直顯示到他回到論證。太5 第一講：「耶穌就是神」一直顯示，到 S0293「有人說耶穌從沒說祂是神；其實證據一大堆」換成下一條。

**播放（按章頁面）**

- 預設跳過批准的範圍：播到範圍起點直接跳到終點。
- 有一個「聽全部」開關。打開時照常播放，逐字稿上這段以灰色或折疊標示。
- 跳過時在逐字稿位置留一行提示，例如「略過一段題外話（3 分 30 秒）」，點它就播放那一段。

## 六、不做什麼

- **不刪原文。** 使命底線：「不以整理後的文章取代原始講道、錄音、錄影、筆記和逐字稿」。題外話仍可聽、仍可讀。
- **不判斷對錯。** 標記不評價他的神學或他對學者的看法，只說這段沒有在論證。
- **不冒充他的話。** 標記與理由是編輯的判斷，頁面上以編輯的名義顯示，不寫成他說的。
- **不刪重要證據。** 反方與他的回答、他給了依據的批評都不標。

## 七、驗收

1. 新實例建立；太5 第一講的 Claim、Evidence 與題外話記錄寫入並回讀一致。
2. 模型對 S0255–S0292 提出題外話標記，S0071 與 S0293 起的兩段不被提出。
3. 編輯批准後，這一講的投影片沒有心臟幻燈片或「受過訓練的眼睛」的要點；負責人案例新增一條檢查這件事。
4. 播放時預設從 S0255 前跳到 S0293，「聽全部」可完整播放。
5. 正式網站在切換前不受影響。

## 八、待定事項

1. **「實例」的意思**：同一台伺服器上的新資料庫（本文的假設），還是另一個獨立的 PostgreSQL 伺服器？
2. **誰是編輯**：批准題外話的是負責人本人，還是另有同工？審閱的介面放在現有審稿頁，還是另做一頁？
3. **其他頁面**：文章與問答是否也略過批准的題外話？本文只規定按章頁面。
