## 一、现状：人子一篇有多少步靠人手

每一步都已有命令，但没有任何东西把它们串起来、记住做到了哪一步，许多检查是会话里临时做的：

| 步骤 | 现有命令 | 人子一篇实际怎么做 |
|---|---|---|
| 1. 定读者问题与范围 | 无 | 手写 `scope.json` 与编辑选定记录 |
| 2. 选材覆盖搜索 | `draft_first_coverage_search` | 命令 |
| 3. 逐项决定纳入／相邻 | `--apply-decisions` | 在对话里讨论，没有写成决定记录 |
| 4. 纳入的 Claim 没有 CVP | 无 | 另一会话手工走 CVP 2.0 |
| 5. 编材料包 | `theological_evidence_packet_runner` | 命令 |
| 6. 写稿 | `draft_first_author_runner` | 命令 |
| 7. 审稿与修订（至多两轮） | `draft_first_review_runner` | 命令 |
| 8. 转人工；负责人意见再开一轮 | `--continue-from`、`--owner-findings` | 意见文件手写；续跑手工拼参数 |
| 9. 来源绑定 | `draft_first_source_binding` | 命令 |
| 10. 登记审稿页 | `register-draft-first-review.py` | 编号与经文范围手填 |
| 11. 终审、发布 | 审稿页 | 负责人 |

靠人手的地方正是出错的地方：

- **续跑拼错**：第一次以负责人意见重开已通过的稿子时，程序带着「已通过」直接结束，留下一份写着通过、实际挂着两条意见的记录（已作废，`review-v2-owner-VOID`）。
- **没有检查的缺陷**：标题前一个无意义字符「়」没有任何程序拦下，是读稿时碰巧看到的；它还让标题被当成一段正文。
- **靠记性的步骤**：审稿 prompt 改动后要先对负责人的 K1–K10 校准，这次是记得才跑；经文引文是否都有来源，是临时写脚本才查出来的。
- **程序缺口在实跑中才暴露**：引文核对把和合本的字形差异、译者夹注、讲道里的删节读法当成不逐字；修订拿不到太 9:6、太 26:28 的和合本。每个缺口都多耗一轮。

## 二、方案

### 2.1 分工：程序管规矩，技能管对话

**大约八成是程序，两成是技能。** 判断标准只有一条：这件事能不能被执行的模型跳过。不能跳过的写成程序。

| 写成程序 | 写成技能 |
|---|---|
| 步骤次序、当前做到哪一步 | 帮负责人把想法落成读者问题与范围 |
| 停在哪里等负责人 | 把覆盖候选用负责人看得懂的话列出，记下决定 |
| 全部检查（见 2.4） | 把负责人读稿时的话写成意见文件 |
| 内容指纹互锁、轮次上限、「已通过的稿子只因负责人意见重开」 | 按次序调用程序，用中文讲结果 |

**技能里不放任何写作或审稿规矩。** 规矩只在作者与审稿的 prompt 里，由测试守住两边一致——一条规矩只让一个环节知道，迟早被另一个环节改掉。这与 `/bible-study` 的做法相同：技能管对话，规矩改动走 PR。

### 2.2 一条总命令：阶段、停点与续跑

每篇文章一个运行目录，内有一个状态文件，逐阶段记下：输入与输出的内容指纹、调用了哪些模型、结论。总命令每次运行从状态文件读出下一阶段，能自动做的一路做下去，遇到停点就停，并写出要负责人决定的内容。负责人决定后再运行同一命令，从停下处接着走；已完成的阶段不重做，输入指纹变了才重做受影响的阶段。

| 阶段 | 自动或停 | 停下时交给负责人什么 |
|---|---|---|
| 范围 | **停** | 读者问题、经文范围、初始立场（由技能协助起草） |
| 覆盖搜索 | 自动 | — |
| 选材决定 | **停** | 每个候选：说什么、为什么相关、建议纳入或相邻 |
| CVP 缺口 | **停**（有缺口时） | 纳入却不属于任何 CVP 的 Claim 清单，交接 CVP 2.0；CVP 完成后续跑 |
| 校准 | 自动；不合即**停** | 审稿 prompt 或模型自上次校准后有变时，先跑 K1–K10，与负责人判定不合的项 |
| 编包、写稿、审稿与修订 | 自动 | — |
| 转人工 | **停**（未通过、`cannot_fix`、两轮用尽） | 未解决的发现、作者的说明、当前稿 |
| 负责人意见轮 | 负责人给意见后自动 | 一次修订加一次完整审稿；意见只能修改或报告无法修改，不能申辩 |
| 来源绑定、登记 | 自动 | — |
| 终审 | **停** | 审稿页链接 |

再开一轮只能由负责人决定；程序不会因为「差一点」自己加轮次（负责人，2026-10-24：「如果有无法解决的问题，转人工」）。

### 2.3 两种入口：专题文章与马太释经

写稿、审稿、修订、来源绑定、登记两者共用；不同的只在**范围怎样定、文章怎样组织**：

| | 专题文章（人子、萬人的贖價） | 马太释经（按段落） |
|---|---|---|
| 范围 | 一个读者问题；负责人选定立场 | 一段经文（如太 16:24-28） |
| 选材 | 覆盖搜索找相关立场与 Claim | 落在这几节经文上的立场、Claim、讲道都要纳入 |
| 组织 | 一个问题、一条主线、一次回答 | 跟随经文次序讲解 |
| 系列 | 无 | 兄弟篇已主答的论证只引结论；共享背景只说一次 |
| 质量档案 | `WQ-theological-topic-essay-v1` | `WQ-matthew-exposition-v1` |
| 发布 | 负责人在审稿页按发布 | 待定（见第四节） |

马太这一边就是 2026-09-10 决定后一直缺的那个按段落的入口。它在总命令里只是范围与组织两处不同，其余阶段原样复用。

### 2.4 新增的程序检查

人子一篇在会话里临时做过、而程序没有的检查，全部变成交稿时的检查，与引文核对同等对待：

1. **无意义与不可见字符**：组合附标、零宽字符、私用区字符出现在正文即拦下。
2. **经文引文都有来源**：每个经文引文块必须找到教授念这节经文或提到这节经文之处（现已在来源绑定里做到，改为交稿时就查）；找不到即拦下，以免被读成文章自己拿经文来用。
3. **校准门**：审稿 prompt 或模型的指纹与上次校准不同，写稿前必须先校准。
4. **CVP 缺口**：选材决定写出后立即列出纳入却无 CVP 的 Claim，不进编包。
5. **意见文件的锚点**：负责人意见的锚点必须逐字出现在当前稿中（现已实作）。

实作中的一处取舍：第 1 项把「无意义」定义为组合附标前面没有可依附的字母（希伯来文元音点跟在字母后面是字的一部分），以及零宽、方向控制与私用区字符；开头的字节序标记不算。

### 2.5 `/topic-essay` 技能

负责人输入题目（或马太经文段落）开始，或不带参数接着做。技能只做四件事：起草范围请负责人确认；把覆盖候选与转人工的发现讲清楚并记下决定；把负责人读稿的话写成意见文件；调用总命令并汇报。它不复述任何写作规则，也不改正文。

## 三、与既有裁定的关系

- **正文不由人手改**（AGENTS.md）：负责人的修改一律经作者修订、再经完整审稿；本方案的意见轮正是这条路，不是例外。
- **每轮一次完整审稿**（AGENTS.md 的 draft-first 审稿调用约束）：意见轮同样只有一次审稿。
- **马太 2026-09-10 的决定**：退役 `CompositionPlan`，在按段落的入口做好并验证之前停下、不退回旧 runner。本方案的马太入口就是为了解除这个停止状态；它做好之前，马太仍然停着。
- **AGENTS.md 中马太的自动发布规则**（审稿每项达标且 Program Audit 零错误即自动发布）是为旧 runner 写的，迁到新流程要不要保留，需负责人重新决定。
