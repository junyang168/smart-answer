# Draft-first 双向审稿：方案

> **读者**：Solution architect、神学编辑
> **类型**：规范
> **状态**：当前（负责人 2026-10-24 批准）
> **与代码对齐**：2026-10-24 核对到 #439 分支的实作（`draft_first_review_runner`、`draft_first_review_agent`、`draft_first_checklist`、`draft_first_coverage_search`）
> **权威范围**：draft-first 专题文章审稿的分工、双向忠实检查的范围与判准、修订循环、选材覆盖检查。写作规则仍由 [Draft-first 文章流程 v1](./draft_first_workflow_v1.md) 管辖。

**目标：文章对教授的论证不增也不减，而且能证明审稿真的查过每一项。** 现行审稿只查「增」，不查「减」；审稿模型只能看喂给它的材料，自己查不了原文。

## 一、现状与问题

现行审稿（`draft_first_review_runner.py`）每轮有四道检查：

| 检查 | 执行者 | 拿到什么 | 方向 |
|---|---|---|---|
| 引文核对 | 程序 | 成稿 + 原文 + 和合本 | 引语逐字 |
| 逐句对材料 | GPT（`gpt-5.6-sol`） | 成稿 + 观点清单 + 原文 | 草稿→原文：有没有说过头 |
| 盲读 | Haiku 复述 + GPT 比对 | 只有成稿 | 读者读到的是不是该读到的 |
| 编辑审稿 | Fable（`claude-fable-5`） | 成稿 + 观点清单 + 路线 + 原文 + 质量维度表 | 完成度与质量评分 |

四个问题，都在《人子》一篇里实际出现过：

1. **只查「增」，不查「减」。** 逐句对材料从草稿的句子出发，找不到没写出来的东西。「每条观点是否落地」只是编辑审稿 prompt 里的一句话，没有程序核对。选材本身（`coverage-inventory.json`：30 个观点中选 17 个，另有 26 条不属于任何观点的 Claim 只记为线索）是关键词检索的结果，文件自注「不是语料完整性证明」，没有任何检查读它；之后新增的 16 条 Claim（如 CL013「人子象征代表神」）也不在其中。
2. **审稿者查不了原文。** 作者（run-3）是带工具的 agent，可以检索全部原文、反复自查；审稿是一次性 CLI 调用，只能就分到手的原文块下判断。查的人比写的人看得少。
3. **两道检查重叠。** 逐句对材料与编辑审稿都读原文、都判忠实度，费用重复，结论可能互相矛盾；编辑审稿与作者同一厂商，跨厂商的约束只保住了一半。
4. **发现未经核实就 blocking。** 对齐把「中文沒有辦法翻」的否定叠加一次而误报；编审 anchor 不是逐字而整轮失效。每个误报都耗掉一轮修订。

## 二、方案

### 2.1 分工

| 检查 | 执行者 | 变化 |
|---|---|---|
| 程序检查 | 程序 | 不变；新增核对双向清单（2.3）是否逐项处置、anchor 是否逐字 |
| 双向审稿 | **GPT 审稿 agent**（`gpt-6.1-sol`） | 取代逐句对材料与编辑审稿；一次完成两个方向与质量评分（负责人，2026-10-24） |
| 盲读 | Haiku 复述 + GPT 比对 | 不变，必须保持只看成稿 |

作者与修订仍是 Opus，审稿全部是 GPT：忠实与质量都跨厂商。现行 runner 的逐句对材料与盲读比对仍用 `gpt-5.6-sol`，实作时一并改为 `gpt-6.1-sol`。

### 2.2 审稿 agent 怎么工作

`codex exec --sandbox read-only` 本身就是 agent：能读文件、跑只读命令。现行客户端在一个空的临时目录里启动它，所以它什么也读不到。新做法与 run-3 作者对称：

- 启动目录是本轮的审稿文件夹：成稿、材料包、观点清单、双向清单、质量维度表，以及只读工具（检索原文、查观点、查 Claim）。
- 它自己决定读什么、读多少，没有 55,000 字的保留上限。
- 每条读取命令都由 codex 的事件流（`--json`）记录：命令原文、退出码与输出。阅读记录以事件流为准，不以审稿自报为准——2026-10-24 实测（`codex-cli 0.162.0-alpha.17.2`，`gpt-6.1-sol`）中，agent 执行了三条命令，自报的「已读来源」却漏掉了检索命令读到的那份。
- `--sandbox read-only` 只禁止写，不禁止读本机其他文件。程序据事件流检查每条命令只涉及审稿文件夹，越界即拒收该次审稿。
- 输出仍受 `--output-schema` 约束。

### 2.3 双向检查

**草稿→原文（不增）。** 与现行逐句对材料相同：清单否定的立场被正面断言、「更可能」被说死、未决关系被合并、材料的沉默被说成经文的沉默、原文没有的事实被补出来。

**原文→草稿（不减）。** 只针对 CVP 与 Claim。程序从材料包生成清单：

- 每条入选观点
- 它的限定与条件（如「每次」，「這裡的人子」限于这些经文）
- 观点之间的张力与来源差异（約5:27 的例外、司提反）
- 每条观察依据（定冠词、中文无法译出）
- 每个未决项
- 论证路线的每一步

审稿 agent 对**每一项**给出处置：「已落地」并附成稿逐字 anchor，或「缺席」并附理由。程序拒收有任何一项没有处置、或 anchor 不是逐字的审稿。这样「查全了没有」可以证明，不靠相信。

**怎样算「减」：** 读者据以支持或反驳的判断不见了，或者变了——立场、限定、张力、论证步骤被删或被改。判准与 Claim 层相同：教授是口头讲道，不是法律文件，不咬文嚼字。

**不算「减」的：**

- 作者自行取舍：生活应用、背景知识、例证与故事。
- 一律排除：口头语、口误、重复、自我推介等与论证无关的内容。
- 不要堆砌材料。反向检查只问论证是否完整，不鼓励把原文搬进来；克制仍是写作规则。

**作者与审稿用同一套。** 上面的清单、「减」的判准、作者自行取舍与一律排除的范围，作者与审稿 agent 拿到的是同一份，写进作者、修订、审稿三份 prompt 的是同一段文字。作者交稿时附上自查：对清单逐项给出与审稿相同格式的处置（run-3 的 `self-check.md` 已有观点落地表，改为全清单、带逐字 anchor）。审稿核对的是作者的处置，而不是另立一套标准；作者没被告知的要求，审稿不得据以 blocking。否则作者按一套写、审稿按另一套查，修订会在两套之间来回。

### 2.4 选材覆盖（写作之前）

「选材有没有漏掉教授在本题上的观点」与草稿无关，放在写作之前做一次，不在每轮审稿重复。

GPT agent（`gpt-6.1-sol`）在编辑选定观点之后、写作之前，检索全语料中与本题相关的 CVP 与 Claim，列出未入选的项目，每项注明它说什么、为什么可能相关。负责人逐项决定：纳入，或记为相邻议题并写明理由。结果写进编辑选定记录，取代现在手工的 `coverage-inventory.json`；材料包据此编译。新 Claim 进入语料后，旧的覆盖记录不再当作当前结论。

### 2.5 发现必须可核实

每条 blocking 发现必须带成稿逐字 anchor；关于原文的发现还须带原文逐字引语。程序核对两者，对不上的发现不进入修订。违反输出契约的审稿沿用现行做法：重试一次，被拒的回答单独存档，不计为审稿。

### 2.6 修订循环：与 CVP 同一模式

作者与审稿 agent 按 CVP 的提议／复核模式协作（[CanonicalViewpoint 设计](../20-knowledge/canonical_viewpoint_design.md) 中 GPT 提议、Opus 完整复核、异议交回提议者修改、再完整复核实际结果）：

1. 作者写稿，并对双向清单逐项自查处置。
2. 审稿 agent 完整审稿：逐项核对清单与作者的处置，给出发现与质量评分。
3. 作者对每条 blocking 发现二选一：**修改**——按条最小修改，不顺手润色别处；或**申辩**——附原文逐字引语说明发现不成立。程序核对双方引语。
4. 审稿 agent 对修订后的**全文**再完整审一次：逐项重核清单（一处修改可能让别处的限定脱落），并对每条申辩裁定接受或维持。审稿对自己的发现有最终决定权，作者只能申辩，不能推翻。
5. 全部通过即结束，批准绑定该稿的精确 SHA；达到修订轮数上限仍有 blocking 时停下，把稿件、未决发现与双方理由交负责人。

两个 agent 不直接对话：程序只传递结构化的发现与回复，双方看不到对方的推理与阅读，审稿保持独立。

**质量评分不重新掷骰。** 忠实检查是逐项处置，每轮完整重核不会漂移；质量维度中本轮修改未触及的，分数仍由程序原样继承。

**审稿调用规则随之修改**（负责人，2026-10-24：多轮写作已证明可行）。现行 AGENTS.md 规定「初稿一次 Independent Editorial Review，每次修订恰好一次 Final Delta Review；不得把修订稿再送完整 Editorial Review」。改为：

> 初稿一次完整审稿；每次修订恰好一次完整审稿，逐项重核双向清单并在同一回答中裁定作者的申辩、给出下一轮发现。不得为凑分另加审稿，也不得在同一轮重复调用审稿。质量维度中未被本轮修改触及的分数由程序继承，不重新评分。

规则的本意——不靠多叫审稿来换取通过、不让未改动的分数漂移——不变；只把「每轮只看改动处」改为「每轮完整重核清单」。审稿 agent 在一次审稿里的读取步骤不是额外的审稿，正如作者的阅读不是额外的写稿。AGENTS.md 与流程文档在实作时同一提交修改，使规则与代码一致。

### 2.7 校准

负责人 2026-10-22 对 draft-A 的人工发现（K1–K10，`agent-comparison-20261022/answer-key-owner-findings.md`）作为常设回归集，存于 `backend/config/draft_first_calibration/`，由 `scripts/draft-first-calibrate.py` 运行。审稿 prompt 或模型变化时重跑，比对命中与误报，才能知道审稿者是否仍与负责人一致。有模式的项由程序判命中；K5 这类只能人判的项列出交负责人。

## 三、与既有裁定的关系

- **使命「不增不减」**：现行只落实了一半，本方案补上「不减」，并以逐项处置使之可证明。
- **写和查不是同一个模型，查忠实的与写的隔着厂商**：由一半落实扩大到全部审稿。
- **审稿调用规则**（AGENTS.md）：由「每轮 delta 审稿」改为「每轮一次完整清单审稿」（2.6）；不加审稿、不重新掷骰的本意不变。
- **克制胜于堆料**、**口头讲道不是法律文件**：写进反向检查的判准，不被它推翻。
- **模型调用只经订阅 CLI**：审稿 agent 仍是 `codex exec`。
