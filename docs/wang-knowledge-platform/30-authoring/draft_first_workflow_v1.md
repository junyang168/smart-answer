# Draft-first 文章流程 v1

> **读者**：神学编辑、Solution architect、Developer
> **类型**：流程
> **状态**：当前
> **与代码对齐**：双向审稿、修订循环与选材覆盖核对到 #439 分支（2026-10-24）；其余未核对（Matthew adapter 尚未实作）
> **权威范围**：draft-first 生产线从输入到负责人终审的运行阶段、各道检查的职责边界、修订循环与停止规则。写作规则的具体条文以 prompt 文件为准；知识层（观点、论证路线）的形成不在本文范围。

## 一、这是什么

Draft-first 是专题综合文章唯一的当前生产线；2026-09-10，负责人也把它定为马太释经的新生产线。旧 Brief 管线和马太 `CompositionPlan` 入口已经退役；历史成品和审稿记录继续只读保留。马太的 passage-specific adapter 尚未实作，在它通过验证以前不得退回旧 runner 继续生产。它的做法一句话说完：

> **先放手写好，再逐句查实。**

写的机器拿到三样东西——要回答的问题、已批准的观点清单、可查阅的教授原文——写出全文。材料较少时直接交付全文；跨多篇来源时采用第三节的分步阅读，不要求全库原文同时进入一次上下文。写之前先查选材有没有漏掉教授在本题上的观点；写完之后，独立的检查双向核对：说的有没有超出教授的意思、教授的判断有没有落下、读者能不能收到答案、文章配不配称为完成。查出问题就退回作者，作者逐条修改或凭原文申辩；最多改两轮，两轮修不干净就停下来交给人。

这条线的设计信条来自实测：**好文章靠好作者读完整材料写出来，忠实靠事后检查保证，不靠事前的条条框框。** 规矩越堆越多的老路（一个缺陷加一条规则）已被证明会把文章勒成合规清单。

## 三、每一步说清楚

### 输入：三样东西，由共享编译器从权威数据产生

没有任何一样需要为写文章新造。读者问题由编辑一句话给出；独立的 `theological_evidence_packet_runner` 从当前 master data 机械编译已批准的观点、论证路线、Claims、来源片段和完整逐字稿／母本，并把依赖与内容 SHA 锁进同一个 `TheologicalEvidencePacket`。作者只读这份 packet，不直接遍历 registry。**观点清单里那份「留而未决的关系」必须随清单同行**——写的和查的都要拿到它，否则文章会把教授没说定的事写成定论（真实发生过一次，四道检查全员漏放，教训换来的规矩）。

### 分步阅读：原文完整保存，按需要查阅

编包入口的 `--source-delivery source_library` 将全部相关原文及其 SHA 保存在材料包中，
不把整批正文直接发送给模型。作者、修订与来源绑定均通过
`draft_first_source_reader` 先查看完整观点清单、条件、范围、已审核关系、来源目录及证据位置，
再请求指定来源的完整编号块；可以继续读取相邻块或其他来源。阅读笔记不是证据或新的批准。
实际读取、选择保留的原文及最终任务的精确输入、原始回复均保存，可重新核对。

每阶段至多十轮读取，保留与单次请求的原文上限为 55,000 字符，完整请求上限为
450,000 UTF-8 字节。超限、未知来源、越界位置、保留未读块或预算耗尽都停止，不能截断。
完整语料分母保留在材料包中；模型只读过部分材料不等于全主题无遗漏，仍须对照主题覆盖清单。
阅读轮不生成编辑评分。审稿不经分步阅读：它是在审稿文件夹里自己读原文的 agent（见第三节「三道检查」）。

读取中断后只复用输入完全一致、且与原始 provider 回复相符的已保存结果；失败请求至多恢复一次，
不重置阅读轮数。审稿的 provider 不可用、或审稿两次违反输出契约时，盲读与程序检查仍可完成，作者可处理已确认的正文问题；
缺失的审稿保持未完成，不能当作通过。若没有可修的正文问题而审稿仍未完成，状态为 `provider_hold`。
若两轮后仍有正文问题则为 `human_review_required`，同时保留错误；两种状态都不允许发布。

当前已批准观点也可由编辑按负责人确定的读者问题直接选择：`--editorial-selection` 指定文章本地清单，
清单中的 `selection_id` 与 scope 的 `structure_revision_id` 一致，并记录 `attribution=church_editor`
和 `decision_basis`。它不批准新的知识结构，不写 Registry，也不继承旧结构的过期观点引用。
每个被选观点仍须为当前已批准版本；全部实际知识依赖继续按 SHA 绑定。旧有结构入口继续可用。

未完成当前版本路线整理的观点会列出编包警告；不能因此声称教授没有论证，也不得用旧版路线
冒充当前批准。若正文展开该处原文，审稿必须实际查阅对应论证，不得凭不存在的路线作出验证结论。

### 写稿的文字要求

写的机器充分阅读所用论证的原文与必要上下文再动笔。规则是功能性的，不规定结构：一个问题发动全文、结尾落一次答案、断言不越观点清单、引文逐字、教授的生动讲法优先采用但导言克制、枝蔓修剪、编辑观察只进编者注；正文以编者口吻直接讲解，不以「教授说」「讲某书时他说」逐段标注出处——出处由来源绑定承担。只有讲到教授本人的生活与经历（如他家里两位 Dr. Wong 的事）时才点名他；释经与神学一律以文章自己的口吻直接讲出，不以「王教授说」引出、不加引号标明是他的话，也不以他为主语（负责人，2026-10-24）。这条同时写进作者、修订与审稿三份 prompt；程序另查正文里的后台用语（材料、母本、本文、各自站立等）、逐段出处标注，以及正文点名教授超过两次，与引文核对一样列为 blocking。原先的写法「引语前交代一次说话人，同段不重复」被读成每段可点名一次，人子一篇第三稿因此出现九处「王教授说」；改为「只在第一次逐字引用时点名」后，修订稿仍点名六次，都是为释经引语交代说话人。观点清单每条带教授的观察依据（`observation_supports`：他在经文用词、冠词、语法、译文上看到什么、支持观点的哪一部分、范围多大）与 subject／predicate／object；没有推理路线的观点仍按观察写，不夸大成逐例证明。`polarity` 是命题本身的正负，已写进核心命题，审稿不再叠加一次否定——「中文沒有辦法翻」曾因此被误报。审稿回答违反输出契约（如 anchor 或原文引语不是逐字）时重试一次；被拒的回答单独保存，不计为审稿，每轮仍只有一次被采纳的审稿。论证骨架按路线走——保证文章与问答等其他产品对同一论证说法一致——但路线不设细节上限，血肉照旧从原文取。没有完整路线的观点（人子一篇 17 条里有 8 条，包括中心主张）在观点清单里标明，论证顺序跟随一篇讲道自己的讲法，不把不同讲道的步骤串起来。清单里每条观点都要落地，一句话带过不算；观点的限定条件是边界，不写成原文没说过的断言。篇幅不设目标（负责人，2026-10-22：言之有物，不是越长越好，也不是越短越好）。读者是神学生和追求的基督徒，作者、审稿、盲读三处同一画像。

### 三道检查：各管一件事，互不代劳

| 检查 | 拿到什么 | 回答什么 |
|---|---|---|
| 程序检查 | 成稿 + 原文 + 和合本 + 双向清单 + 作者自查 | 引号里的字是不是一字不差（经文引文块也可对和合本：文章据以论证的经文必须完整摆出，教授常只报出处不念全文，所以程序取来源提到的各章和合本作第二依据，逐章记 SHA；标点不计，字须一字不差。行内引号里是教授的话，只对讲道）；正文有没有后台用语、逐段出处、点名教授超过两次；作者自查是否逐项处置了清单 |
| 盲读测试 | **只有成稿** | 一个不知情的读者读完，能不能用一句话说出正确答案、保住该保的限定。故意用最小的模型——它就是普通读者的替身 |
| 双向审稿 | 审稿文件夹：成稿、作者自查、双向清单、观点清单、路线、未决清单、全部原文、质量维度表与只读检索工具 | **不增**：每句话有没有说过头——清单否定的立场被正面断言、「更可能」被说死、未决的关系被合并、材料的沉默被说成经文的沉默、原文没有的事实被补出来。**不减**：清单逐项核对作者的处置，判断有没有落地、有没有被改动。**完成度**：论证每一步是不是教授在同一篇讲道里真走过、有血肉但不过分的度、每个维度过没过自己的最低线 |

写的和查的**永远不是同一个模型，也不是同一个厂牌**：作者与修订是 Claude Opus，审稿是 GPT（`gpt-6.1-sol`）。

**双向清单**由程序从材料包生成，只含教授 CVP 与 Claim 层的判断：观点、观点的条件、观察依据、张力、未决项、论证路线。作者交稿时对每一项给出处置——落地（附成稿逐字片段）、缺席（附理由）、走样（附理由）；审稿用同一份清单核对。生活应用、背景知识、例证由作者取舍；口头语、口误、重复、自我推介一律不写；清单只问论证是否完整，不鼓励堆砌材料。这段规则一字不差地写进作者、修订与审稿三份 prompt（`draft_first_two_way_rules.md`）。

**审稿是一个 agent**：`codex exec --sandbox read-only` 在本轮的审稿文件夹里启动，自己决定读哪些原文、读多少，不受分步阅读的保留上限约束。`--sandbox read-only` 只禁止写，不禁止读本机其他文件，所以程序逐条检查 codex 事件流里记录的命令，任何越出文件夹的读取都使这次审稿作废。阅读记录以事件流为准，不以审稿自报为准。

**发现必须可核实**：每条发现带成稿逐字片段；关于教授判断被落下或改动的发现，还须带原文逐字引语。程序核对，对不上的整份审稿被拒收重试一次，不进入修订。

### 修订循环：与 CVP 同一模式

必须修的问题汇总退回作者，每条带编号。作者对每条恰好回应一次：**修改**（按条最小修改，不许顺手润色别处）、**申辩**（附原文逐字引语说明发现不成立；只有审稿的发现可以申辩，程序检查与盲读的发现不能），或**无法在原文范围内解决**（交负责人）。修订稿连同重做的自查再完整审一次：审稿逐项重核清单——一处修改可能让别处的限定脱落——并对每条申辩裁定接受或维持，维持的重新列为发现。审稿对自己的发现有最终决定权。没被本轮问题触及的质量维度分数由程序原样继承，不重新掷骰。最多两轮；仍有问题就停下、写明原因、交给人——**机器永远不硬发**。两个模型不直接对话：程序只传递编号的发现与回应。

这取代了先前「修订后只复查改动段落与结尾」的 delta 审稿（负责人，2026-10-24：多轮写作已证明可行）。方案与理由见 [Draft-first 双向审稿：方案](./draft_first_two_way_review_solution.md)。

### 选材覆盖：写作之前

作者只从材料包写，审稿清单也从同一份材料包生成——选材时漏掉的，写不出来，也查不出来。所以编辑选定观点之后、写作之前，`draft_first_coverage_search` 让一个 GPT agent 检索全库当前的观点与 Claim，列出与本题相关却未入选的项目，每项注明说什么、为什么相关、建议纳入还是记为相邻议题。负责人逐项决定并写明理由，程序把决定写进新的编辑选定记录；纳入的观点进入材料包。不属于任何观点的 Claim 不能单独进入材料包，决定纳入时记为需先做 CVP 整理。新 Claim 进入语料后，旧的覆盖记录不再当作当前结论。

### 来源绑定与登记：给审稿的人配全证据

绑定回答「这段话教授在哪里说过」：每段标出原文逐字片段，程序逐字核实，对不上的一律丢弃并记录（第一次实跑就丢弃过全部 37 条错误提案，零错误进页面）。讲道出处自动带录音跳转；论证段另附教授这条论证的步骤展开。稿件、检查记录、绑定、材料包四者的内容指纹互锁登记——事后改动任何一份，审稿页立刻显示「已改变」。

### 负责人终审：流程里唯一的人工点

审稿页上逐段看原话、听录音、走论证。发布键只有人能按。材料不足时文章宁可少一句应用也不编造（平台既有裁决）；同理，检查修不干净时宁可停下也不放行。

## 四、规矩从哪里来

写作规则不是设计出来的，是**裁决累积出来的**：负责人每一次具体的编辑意见（「细节过多」「编辑观察入注」「结尾稍有重复」）被泛化成一条与具体文章无关的规则，进入规则文件，各道检查同步引用同一条界线——规矩只让一个环节知道，迟早会被别的环节改掉，这是平台反复付过学费的教训。外部复查（另一家模型的审计）同样走这条路：发现 → 验证 → 规则或代码 → 全线生效。

## 五、Brief 与马太 CompositionPlan 入口已经退役

专题综合文章不再生成 Brief，也不再调用旧的「按 Brief 撰写 → Grounding／Program Audit」半套。历史 Brief 版文章、审核 artifact 和审稿页渲染继续只读可见；它们不是新生产入口。证据包编译器是知识层与文章层之间的共享地基，已从旧 Composition runner 独立出来。

2026-09-10，负责人进一步退役马太释经的 `CompositionPlan` 入口；马太新稿也必须采用 draft-first 的「先写、后核」边界。现有专题命令不能冒充 passage adapter，旧 Matthew runner 也不能在迁移完成前作为 fallback。该决定未改变微讲道流程。

## 六、Developer 附录

以下是当前已实作的**专题文章 adapter** 命令（全部模型调用走订阅 CLI，不直连 API）。它们不构成马太释经的可运行入口；马太 adapter 完成前不得用旧 `--plan-id` 命令替代：

```bash
# 先从当前 master data 编译 SHA-bound packet（不会调用模型）
backend/.venv/bin/python -m backend.pipeline.theological_evidence_packet_runner \
  --scope <scope.json> --output-dir <run>/packet

# 只验证编包输入与输出；仍写出 packet 供检查
backend/.venv/bin/python -m backend.pipeline.theological_evidence_packet_runner \
  --scope <scope.json> --output-dir <run>/packet-dry-run --dry-run

# 选材覆盖：agent 列出未入选的观点与 Claim（一次模型调用；不批准、不写库）
backend/.venv/bin/python -m backend.pipeline.draft_first_coverage_search \
  --scope <scope.json> --editorial-selection <selection.json> --output-dir <run>/coverage
# 负责人对 coverage-candidates.json 逐项决定后，写出新的编辑选定记录
backend/.venv/bin/python -m backend.pipeline.draft_first_coverage_search \
  --scope <scope.json> --editorial-selection <selection.json> --output-dir <run>/coverage \
  --apply-decisions <decisions.json>

# 写稿（draft.md + self-check.json）
backend/.venv/bin/python -m backend.pipeline.draft_first_author_runner \
  --packet <run>/packet/theological-evidence-packet.json --reader-question "<一句话>" \
  --output-dir <run>/author-v1

# 三道检查 + 修订循环（读取 draft.md 旁的 self-check.json）
backend/.venv/bin/python -m backend.pipeline.draft_first_review_runner \
  --draft <run>/author-v1/draft.md --packet <同上> --output-dir <run>/review-v1

# 来源绑定
backend/.venv/bin/python -m backend.pipeline.draft_first_source_binding \
  --draft <run>/review-v1/final.md --packet <同上> \
  --output <run>/review-v1/source-bindings.json

# 登记进审稿页
backend/.venv/bin/python scripts/register-draft-first-review.py \
  --review-id <id> --passage "<经文>" --review-dir <run>/review-v1 \
  --bindings <run>/review-v1/source-bindings.json --packet <同上>

# 校准：审稿 prompt 或模型变化后，对负责人 K1–K10 重跑（一次审稿调用）
backend/.venv/bin/python scripts/draft-first-calibrate.py --output-dir <run>/calibration
```

模型分工：写稿与修订 `claude-opus-5`；双向审稿、盲读比对与选材覆盖 `gpt-6.1-sol`（codex CLI；审稿与选材覆盖以 agent 方式在各自文件夹内运行）；盲读 `claude-haiku-4-5`。写作规则在 `backend/pipeline/prompts/draft_first_topic_author.md`，双向规则在 `draft_first_two_way_rules.md`，审稿判准在 `draft_first_two_way_review.md`。校准答案在 `backend/config/draft_first_calibration/`。质量维度表沿用 `WQ-theological-topic-essay-v1`。每次检查调用的 prompt、输入、输出三重内容指纹记录于 `review-run.json`。
