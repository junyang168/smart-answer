# 聆聽投影片的論證圖

> **讀者**：神學編輯、Developer。
> **類型**：規範。
> **狀態**：當前。
> **與代碼對齊**：2026-11-18（#787 重開後的修正）。
> **權威範圍**：論證圖如何進入聆聽投影片，以及發布前的驗收條件。

## 1. 目標

聽眾在教授講到一條論點時看到相應的圖。圖隨論證層更新，播放時間取自已校對的原文。出版時連同對應的聆聽單元與章摘要一起驗收。

## 2. 選圖與署名

- 出版流程從論證庫讀目前有效的 Claim、指向它的 `supports` 連接、Observation、視覺 SourceFragment 和來源文件。圖在別講或母本時也按這條連接選入。獨立論證 Eval 的 golden keys 不參與選圖。
- 視覺片段需通過 SVG 安全校驗，完整圖檔須符合資料庫所存的 SHA-256。作者類型取自同一個片段的來源證明。來源名稱和類型供內部核對，聆聽畫面只呈現圖。缺少或互相矛盾的作者證明時，該圖不進投影片。
- A「宗主國與附庸國的約」、B「兩律法的重疊」和 D「登山寶訓（論彌賽亞／門徒的使命）」用各自核實的教授來源。C「登山寶訓的文學結構」使用編輯署名。
- 有圖的投影片在生成時只填一個 `diagram_ref`，對應論證層提供的圖。程式查這張圖是否連到本張投影片的陳述句，並帶入圖檔。

## 3. 出場和播放

- 圖在他開始講這個論證時出現。程式取本張投影片內連到這張圖的 Claim 最早的一句：Claim 的陳述句、Evidence 的錨點句，或引用該 Claim／其 Evidence 的要點句。陳述句常是他的歸納。第 1 講的 D 若等陳述句 S0018（210.6 秒），他在 S0008（135.4 秒）起已經把兩大段講完了。
- 圖歸在選了它的投影片，沿用字幕的時間換算，跳播進入也一樣。到了別張投影片或另一段錄音就收起。
- 每張投影片有一張圖或沒有圖。
- 圖照原樣顯示：他的 SVG 是白底畫的，放在白色卡片上，不重排、不反色。負責人 2026-11-18 指出，按四張圖各寫一套 HTML 版面、按 SVG 雜湊對應，是為每張圖做特例，而且很難看。點圖放大到全螢幕，小螢幕上看細字。
- 要點和字幕在有圖時照常顯示，不收起。要點是聽眾跟上論證的主線。

## 4. 驗收

| 案例 | 可接受結果 |
| --- | --- |
| 第 1 講的結構圖 | C、D 各自放在相關投影片，保留各自圖中的文字與層次 |
| 第 1 講的 D | 在 S0008 他開始講兩大段時出現，不等到 S0018 的歸納 |
| 第 2 講的 A、B | 各在他開始講自己的 Claim 時出現 |
| 有連接但沒有保留的陳述句 | 不顯示圖；無關的 Evidence 要點不能決定出場 |
| 同張投影片被剪成兩個播出片段 | 圖只在包含出場句的播放片段顯示 |
| 更正版的論證層 | 只有在更正憑證與原始候選都相符時，才能沿用原始分組 |
| 來源證明或圖檔更動 | 署名無法確認時不選圖；已綁定的圖檔若不符 SHA-256 或安全校驗，停止建立該版本 |
| 320×568、390×844 及桌面 | 核對未到時間、跳到時間之後和切段。用實際圖確認原樣顯示（白卡、無濾鏡）、寬度落在畫面內、要點仍可見、可點開放大 |

圖的取材與出場納入既有 Slide Eval。整體聆聽 Eval 另核對圖落在實際錄音片段的發言句，瀏覽器量測與其他介面證據共同綁定同一份聆聽目錄。更新論證時，傳入本次目標版本對照表 `--expected-versions`，舊版資料須列為尚待更新。瀏覽器已有原證據時，以 `node web/evals/listening-diagrams.cjs <catalog.json> <browser-evidence.json>` 補入測量，再把產出的 JSON 交給 `chapter_listening_eval`。完整報告仍要核對資料版本及其他聆聽檢查。

## 5. 要點的時間

過晚和過早一樣是錯。負責人 2026-11-18 指出：第 1 講他在 S0015（186.0 秒）說「第五章十三節到第七章二十九節…門徒的使命」，畫面要到 198.6 秒才出這一點。原因是模型把它和兩句後的「認識神之後有生命上的反應」合成一條，舊規則要合併的要點等所有意思講完才出現。

- 生成規則：一條要點只寫他在一處講出的一個意思。意思分在不同句時拆成幾條，各綁各自首次講出的句子。
- 程式檢查：他講進另一步論證，畫面最新的要點還屬於別的 Claim，超過 4 秒就退回模型（`chapter_slide_claims.STALE_SECONDS`）。原本容許三句，兩句 12 秒的延遲因此沒有被擋下。
- 負責人案例：`chapter_slide_cases.json` 記下 S0015，每次生成都查。

## 6. 成品的語義 Eval

生成稿先通過程式檢查，再把實際會顯示的投影片、同版原文與論證交給語義 Eval。逐張驗收忠實、承重內容、時間和已讀經文。時間一項同時查過早與過晚。標題一換張就可見，結論和故事結果須等到說出時才顯示。對比和首尾呼應應保留兩端的理由與結論。

用 `python -m backend.pipeline.chapter_slide_eval <slides> <selection> --run <receipt>` 呼叫評審模型，寫出同版 Eval 檔。評審模型須與寫投影片的模型不同（預設 `claude-opus-5-5`）。Eval 檔帶模型名稱和原始回覆及其雜湊。每次都重看每一張，不沿用先前的判定。第 1 講原有的 Eval 檔由寫投影片的人手寫，標著「沿用…該項未變」，那個 12 秒的延遲就這樣過關。`--verify <receipt>` 查版本、完整性與這份執行紀錄，不呼叫模型。

新稿的聆聽 Eval 和發布共用這份檔案。單元資料把它存為 `<lecture>.semantic-eval.json`，與 `<lecture>.slides.json` 及 `<lecture>.selection.json` 放在一起。實際成品的正反例存於 `backend/tests/fixtures/chapter_slides/actual_candidate_eval_gold.json`。
