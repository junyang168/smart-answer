# 微講道：三至五分鐘短篇教導 Use Case

> **讀者**：神學編輯
> **類型**：說明
> **狀態**：目標設計，不表示欄位與閘門均已實作
> **與代碼對齊**：不適用
> **權威範圍**：微講道產品的目標形態。

> 狀態：產品用例與目標設計。現有 `/resources/micro-sermon` 與 `/admin/micro-sermon` 是可繼續使用的公開與管理介面；本文件定義它們如何接入王守仁教授共享知識平台。本文不表示目前所有欄位與審核閘門均已實作。

## 1. 為什麼需要微講道

王教授的講道通常論證完整、材料豐富，但一篇往往長達一小時以上。許多讀者在社交媒體環境中只能先投入三至五分鐘；若沒有短篇入口，他們可能尚未聽見一個完整問題和答案，便已離開。

微講道的目的不是把長講道簡化成口號，而是從共享知識中選出一個能在三至五分鐘內忠實講清楚的問題，保存教授的核心判斷與必要理由，讓讀者先理解一件事，再按需要進入完整講道、釋經文章或專題論述。

現有網站上的「微講道」是這一方向的早期探索。下一階段應保留既有播放與管理介面，補上共享主張、論證關係、精確來源及失效傳播，使它成為知識平台的正式產品出口，而不是另一套獨立內容資料。

## 2. 核心產品原則

1. **一篇只回答一個中心問題。** 不在三至五分鐘內概括整篇講道或完整神學專題。
2. **保留最小完整論證。** 除了結論，也要保留讀者理解結論所需的兩至四個理由、經文或限定。
3. **不是機械截短長文。** 系統先選擇合適的問題與知識子圖，再為短篇媒介重新編排。
4. **與長篇成果共享知識。** 微講道、釋經、專題與問答使用相同的 `Claim`、`Relation`、`Citation` 和 `SourceFragment`，不得另建私有神學語義。
5. **清楚標明聲音與歸屬。** 教授原聲剪輯、教授明說、直接推論及編輯綜合不可混為一談。
6. **短而不斷章取義。** 若刪除上下文會改變教授原意，該材料不適合直接剪成微講道；可改用明確標示的編輯綜合短講，或暫不製作。
7. **短篇是入口，不是替代品。** 公開頁應連向完整講道、相關釋經／專題及可核查來源。

## 3. 兩種製作模式

### 3.1. 教授原聲片段（`source_excerpt`）

從一篇原始講道中選取能相對獨立成立的三至五分鐘錄音或錄像：

- 保存媒體來源、開始與結束時間；
- 顯示對應逐字稿並高亮精確片段；
- 只做不改變意思的剪輯，例如去除長停頓或重複口頭語；
- 若片段需要前文才能理解，加入簡短編輯導言，但不得冒充教授原話；
- 公開頁標示「王教授原聲」。

此模式最接近教授現場表達，但不適合論證散布在多個不連續段落或多篇講道中的題目。

### 3.2. 編輯綜合短講（`editorial_synthesis`）

由編輯根據已審核的跨講道知識子圖，寫成三至五分鐘可連續聆聽的短講：

- 可以整合一篇或多篇講道中的相關主張；
- 每個實質結論都連到共享主張與來源；
- 必須明確標示為「根據王守仁教授講道整理」，不可讓讀者以為是教授原錄音；
- 編輯補充、過渡語及應用需保留編輯歸屬；
- 公開頁提供「查看依據」與「深入閱讀」。

此模式適合教授在多處反覆談論、但沒有一段原聲可以獨立構成完整短講的題目。

## 4. 從共享知識到微講道

```mermaid
flowchart LR
    S["講道、逐字稿與筆記"] --> K["共享知識：問題、主張、關係與來源"]
    K --> Q["選定一個可在 3–5 分鐘回答的問題"]
    Q --> G["建立最小完整論證子圖"]
    G --> P["微講道 Composition Plan"]
    P --> X["教授原聲片段"]
    P --> E["編輯綜合短講"]
    X --> R["來源與語境審核"]
    E --> R
    R --> A["雙模型忠實度復核"]
    A --> U["既有微講道管理與公開頁"]
    U --> L["完整講道、釋經、專題與問答"]
```

選材時不是先問「哪一篇長講道可以切五分鐘」，而是先問：

> 哪一個讀者真正會問的問題，已經有一條足夠清楚、可溯源而且不需要大量先備知識的論證鏈？

## 5. 微講道的編排計畫

每篇微講道使用正式的 `CompositionPlan`，而不是只保存影片標題。計畫至少包含：

- 中心問題；
- 一句簡明回答；
- 必須保留的核心主張；
- 支持、限定、反駁或應用關係；
- 必要經文與來源；
- 製作模式；
- 目標長度與讀者；
- 開場語境；
- 兩至四個論證步驟；
- 結尾重點或生活回應；
- 不在本篇展開的內容及延伸連結；
- 資料缺口與不可省略的限制條件。

如果一個題目不能在三至五分鐘內保留最小完整論證，編排決定應當是拆分為系列、改做長篇，或暫不製作，而不是強行壓縮。

## 6. 與現有資料和 UI 的關係

現有 `MicroSermon` 記錄及 `micro_sermons.json` 保存公開播放所需的標題、系列、YouTube URL、簡介、標籤、推薦狀態與發布日期。這些欄位仍屬於**交付投影**，不需要搬進共享知識圖。

知識平台應為每個受管理的微講道補充以下連結資料：

```json
{
  "sourceMode": "source_excerpt | editorial_synthesis",
  "centralQuestion": "...",
  "durationSeconds": 240,
  "productPlanId": "CP-MS-...",
  "knowledgeSnapshotId": "KB-...",
  "claimIds": ["CL-..."],
  "relationIds": ["CR-..."],
  "citationIds": ["CIT-..."],
  "productDependencyIds": ["PD-..."],
  "reviewStatus": "candidate | ai_reviewed | needs_human | approved | invalidated"
}
```

這些欄位可以先由獨立的知識投影記錄引用現有微講道 ID，不必立即破壞現有 JSON API。等試驗證明穩定後，再決定是否合併 API schema。

### 公開頁

普通讀者只需看到：

- 標題與中心問題；
- 三至五分鐘播放器；
- 一句內容簡介；
- 主要經文或主題；
- 「查看原始講道與來源」；
- 「深入閱讀相關釋經／專題」；
- 若為編輯綜合，清楚顯示整理者歸屬。

不得把內部 claim ID、relation ID、模型診斷或審核術語直接暴露給普通讀者。

### 管理頁

同工需要看到：

- 製作模式與中心問題；
- 編排計畫和短講稿；
- 使用的主張與論證順序；
- 每項主張的原始講道、逐字稿高亮與媒體時間；
- 剪輯開始／結束位置；
- AI 復核結果、尚待處理問題和發布狀態；
- 受到上游修訂影響時的失效警告。

## 7. 審核與發布閘門

公開前至少檢查：

1. 使用的主張都在該交付物的最小知識子圖內達到要求的成熟度；
2. 支持結論的引文能回到正確講道、說話者和時間位置；
3. 聽眾發言或教授所反對的立場沒有被誤當為教授主張；
4. 三至五分鐘的剪裁沒有刪去改變結論的前提、限定或反例；
5. 經文與教授實際使用的經文區分清楚，不以編輯補充冒充教授依據；
6. `editorial_synthesis` 的編輯語句與教授原話有清楚歸屬；
7. Claude 進行獨立忠實度復核，OpenAI 接受並修正或提出異議；持續分歧才進入人工隊列；
8. `ProductDependency` 已建立，能在上游主張、來源或關係失效時找到並阻止錯誤版本繼續發布。

AI 復核只檢查來源忠實度、論證完整度、歸屬、遺漏與媒介適配，不進行神學批評。公開是否合宜仍由教會編輯決定。

## 8. 失效與持續修訂

微講道不是發布後便與知識庫斷開。若它依賴的主張被否決、實質修訂，或來源錨點變成 `stale_paragraph`／`non_verbatim`：

1. 系統產生 `ImpactEvent`；
2. 對應 `ProductDependency` 變成 invalidated；
3. 管理頁顯示需要重新審核或重新剪輯；
4. 新 Active Snapshot 不得繼續輸出失效版本；
5. 編輯決定修訂、撤下或保留歷史版本並附說明。

## 9. 第一輪驗證

核心九篇講道可同時驗證長篇專題與微講道，但不預設每篇都要產生短片。第一輪可選四至六個題目，例如：

- 什麼是「宗主國與附庸國的約」？
- 王教授為什麼強調「因信成義」而不是「因信稱義」？
- 血、立約與赦罪有什麼關係？
- 基督為什麼是約的中保？
- 律法與恩典真的是彼此對立嗎？

試驗宜同時包含至少兩個教授原聲片段和兩個編輯綜合短講，以驗證兩種模式的來源、編排、審核與公開呈現。

## 10. 完成標準

本 use case 的第一階段完成，不以「產生很多短片」衡量，而以以下能力是否跑通衡量：

- 一個問題能由共享知識投影為可審核的微講道計畫；
- 原聲片段與編輯綜合使用同一主張和來源身份；
- 公開頁簡單易懂，同時能進入完整講道和深入閱讀；
- 管理頁能核查每個實質結論與剪輯語境；
- 雙模型復核能把真正分歧送入人工隊列；
- 上游修訂能準確找到並使受影響的微講道失效；
- 微講道沒有形成與釋經、專題和問答平行的私有知識庫。

## 11. 實施次序

1. 為現有三篇微講道建立來源與現有共享主張的對應，記錄無法追溯的缺口。
2. 建立 `PP-micro-sermon-3-5min` Publication Profile 與第一版 Composition Plan schema。
3. 從核心九篇選擇四至六個適合短篇回答的問題，不按標題機械切片。
4. 建立原聲與編輯綜合兩種候選，完成來源定位和雙模型復核。
5. 在現有 `/admin/micro-sermon` 增加知識依據與審核區，而不是另造管理站點。
6. 在現有 `/resources/micro-sermon` 增加來源、深入閱讀與整理者歸屬。
7. 驗證失效傳播後，再決定是否擴展現有 API model 及批量處理更多講道。
