# 文檔維護約定

> **讀者**：所有會修改本目錄文檔的人與 agent。
> **類型**：規範。
> **狀態**：當前。
> **權威範圍**：本目錄下每一份文檔的頭部格式、體裁邊界、用字與編號。新增或修改文檔前先讀本文。

本目錄有四十多份文檔、一萬四千多行。在本文之前，沒有任何一份說明自己該怎麼維護，於是文檔只能靠**追加**生長，留下了這些痕跡：章節編號出現 `5.4a`、`5.4b`、`6.0`；一句「因此採用三項原則」下面列了四項；README 的「當前實施進度（2026-08-15）」標題日期比它自己的內容還舊。

四條約定，都是為了讓下一個人不必讀完全文就知道該不該信這一頁。

## 一、每份文檔必須有狀態方框

```markdown
> **讀者**：普通基督徒 | 神學編輯 | Solution architect | Developer
> **類型**：規範 | 流程 | 記錄 | 說明
> **狀態**：當前 | 已被 `<path>` 取代
> **與代碼對齊**：<日期>（核對到 <commit sha>） | 未核對 | 不適用
> **權威範圍**：<這份文檔對什麼有決定權>
```

**放在開頭還是文末？** 預設開頭——先看方框再決定要不要往下讀，尤其要看清它是「規範」還是「記錄」。**例外：以目標或結論開篇的文檔放文末**，做成「關於本文檔」一節，因為讀者的第一行應該是那句目標，不是元數據。[Solution Architecture](./00-overview/solution_architecture.md) 是這樣做的。

**`讀者` 決定這份文檔能出現什麼詞。** 寫給普通基督徒的文檔裡不出現 `ViewpointKnowledgeProjection`；寫給 developer 的文檔裡不做神學判斷。改完一份文檔，用它聲明的讀者身分從頭讀一遍再定稿。

**`與代碼對齊` 必須誠實。** 沒有逐條核對過就寫「未核對」，不要寫日期。這一行的用處正是讓讀者知道哪些頁面還沒人驗過。

## 二、記錄不進規範

四種體裁的效力不同，**不可混在同一份文檔裡**：

| 類型 | 它回答什麼 | 效力 | 更新方式 |
| --- | --- | --- | --- |
| **規範** | 這件事必須怎麼做 | 實作和其他文檔都必須遵守 | 原地改，永遠保持當前 |
| **流程** | 分哪幾步、誰在哪一步判斷 | 照著執行 | 原地改 |
| **記錄** | 某年某月某次試驗得到什麼結果 | 只說明那一刻 | **只增不改**，過時了就歸檔 |
| **說明** | 某個頁面或工具怎麼用 | 供操作參考 | 原地改 |

帶日期的實測數據寫成獨立的「記錄」類文檔，**不要嵌進規範的編號章節**。一份規範裡出現 `### 14.2 雙軸縱向驗證實施記錄（2026-08-10）` 這樣的小節，讀者會把兩年前的一次試驗當成今天要執行的步驟。

同理，一份「記錄」類文檔裡不要藏規則。如果某條規則只寫在某次試驗報告裡，它實際上等於不存在。

## 三、用字與命名

- **散文用繁體還是簡體，不必強求統一。** 本目錄兩種都有，讀者都看得懂，不值得為此改動既有文檔。
- **但作為配置值、UI 標籤或程式字面值出現的中文，必須和代碼逐字節一致。** 這不是風格問題：代碼是繁體——`backend/pipeline/seed_catalog/generator.py:20` 的 `CONTENT_CATEGORIES = ("釋經", "神學意義", "生活應用", "附錄")`。曾經有一份規範把同一個值寫成簡體，兩份規範對同一個值給出不同的字節，結果 `backend/pipeline/transcript_pipeline.py:857` 只好留一張繁→簡別名表在運行時兜底。
- **引用其他文檔的標題時，保持該文檔自己的標題用字**，不要為了統一而改寫別人的名字。
- 技術名詞保持英文原文（`ChangeSet`、`ArgumentRoute`、`fail closed`），不翻譯、不音譯。

## 四、編號與長度

- **一份文檔內只用一種編號寫法。** 不要 `### 1.1.`（帶句點）和 `### 10.1`（不帶）並存，也不要某幾節乾脆不編號——沒有編號的小節無法被引用，只能指行號。
- **不要字母後綴。** `5.4a`、`5.4b`、`6.0` 都是在既有小節前後硬塞新內容的產物。新內容如果重要到需要自己的小節，就重新編號；如果不重要，就併進去。
- **每份文檔開頭要有目錄**，除非全文短於 150 行。
- 一個小節長到讀者無法一次讀完，就拆開。一段超過 400 字，就分段。

## 五、修改文檔時

1. 先看頭部方框：這份是規範還是記錄？我要改的東西屬於哪一種？
2. 文檔與代碼不符時**以代碼為準**，把文檔改對，並更新 `與代碼對齊` 那一行。不要在文檔裡遷就一個已經不存在的實作。
3. 一份文檔被另一份取代時，不要刪除它——移進 `archive/`，並在 `狀態` 寫明被誰取代。審計需要看見結構是怎麼變的。
4. 改完後跑 `scripts/check-docs.py docs`，確認相對鏈接、錨點和 mermaid 節點 ID 都沒壞。

   ```bash
   python3 scripts/check-docs.py docs
   ```

   目前它有一個已知的既有失敗：`docs/notes-to-sermon-agent/functional_spec.md:120` 指向一個
   不存在的附錄。那份文檔屬於另一個項目，留給該項目處理。

## 六、定稿前逐条過一遍

寫的時候記不住，所以定稿前照這張表走。前三條機器能查，跑 `python3 scripts/check-docs.py docs`；後三條只能人看。

| | 查什麼 | 誰查 |
| --- | --- | --- |
| 1 | 相對鏈接、錨點是否都能解析 | 機器 |
| 2 | mermaid 節點 ID 有沒有重複 | 機器 |
| 3 | ER 圖裡的每個實體，正文有沒有描述 | 機器 |
| 4 | **正文裡每個名詞，術語表有沒有？沒有就解釋或換掉** | 人 |
| 5 | 圖裡畫的每個框，下面的表有沒有 | 人 |
| 6 | 每個數字、日期、版本，是不是剛從輸出裡讀來的 | 人 |

第 4 條最常漏。從代碼裡搬來的字段名（`scope`、`lease`、`attestation`）在代碼裡是標識符，搬進散文就成了黑話——讀者要的是它的意思，不是它的名字。
