# 205 篇讲道普查后的总体设计验证 v1

> 状态：设计验证记录，不是教授思想体系的人工定稿，也不是神学事实核查结论。验证日期：2026-08-07。

## 一、验证问题

本轮不是继续从少数样本推测教授的思想，而是用当前可用的 205 篇讲道逐字稿反向检验整个项目设计：

1. 论证知识层能否忠实保存教授讲了什么、凭什么这样讲；
2. 释经轴和神学思想轴能否共享同一批主张，而不互相混淆；
3. 篇章编排计划能否支持以经文为中心的释经讲座和跨讲道主题专论；
4. 同一知识基础能否支持文章、智能问答、搜索、课程和研究；
5. 哪些问题是总体设计缺失，哪些只是第一遍普查尚未实现。

## 三、总体结论

### 3.1. 不需要推倒重来

下列核心设计经完整语料压力测试后仍然成立：

1. **来源档案层**：逐字稿、录音录像和笔记保留为原始证据；
2. **论证知识层**：问题、主张、证据步骤、推论桥、反对观点、应用推理和彼此关系分开保存；
3. **双轴组织**：释经按卷章节目组织，神学思想按跨讲道主题组织，但引用同一个主张图；
4. **篇章编排层**：文章不是知识库的机械投影，而是有目的、有读者、有详略和转介决定的新著作；
5. **多产品输出**：文章、智能问答、搜索、课程和研究都从审核状态明确的同一知识基础取材；
6. **审核与事实核查分离**：先确认“教授是否这样说和这样论证”，再独立核查历史、原文、翻译或神学判断。

因此，论证知识层不是多余的中间格式。若直接从 205 篇逐字稿生成文章，每一次写作都会重新猜测哪些话相同、哪些是理由、哪些是反对观点，智能问答也无法复用文章中隐含的论证关系。

### 3.2. 现有候选主干必须继续保持可修改

完整语料继续支持“候选释经与神学思想主干 + 经文／应用／时间三条横向轴”的总体形状，但当前一级结构仍只是版本化候选基线，不能因数量暂时为七就冻结成“教授的七条神学”。

新增 93 篇使下列材料明显增厚：教会论、牧养书信、教会秩序与建造、属灵恩赐、祷告、服事与领导、异端辨识、家庭及处境伦理。它们需要在跨讲道综合和人工审核后决定是：

- 现有主干的二级分支；
- 横向应用轴的一部分；
- 独立一级候选结构；
- 或只是一组经文／书卷系列特别集中的材料。

在完成归组审核前，不应仅凭关键词频率把它们自动升格。

### 3.4. 五项机器设计发现的人工复核

| 机器发现 | 对当前设计的人工判断 | 处理 |
|---|---|---|
| 释经方法内部混合不同证据步骤 | **架构已有，普查实现不足。** `EvidenceStep`、`InferenceBridge`、`ScriptureEvidence`、`OriginalLanguageJudgment` 和 `ExternalEvidence` 已能区分；不需新造平行“方法主张”对象。 | 扩充 `EvidenceStep.step_type`，普查 v2 采集，并用 `produced_claim_ids` 记录它服务的结论。 |
| 提问、暂定解释、后来回答和仍未回答内容被同级汇总 | **部分缺失。** `QuestionRecord` 已有回答状态，但跨讲道生命周期不够完整。 | 增加提出来源、解决来源、前后问题和状态历史。 |
| 教会治理与秩序仅归为一般应用 | **基线与本体均需扩展候选。** 这些材料已有 22 篇治理材料、10 篇恩赐秩序材料及 14 篇共同生活材料，不能先验降格为个别应用。 | 建立“教会与服事”候选神学／实践领域；增加会众、领袖、教导者、受纪律者等角色和治理目标。 |
| 持续信心、背弃警告与神保守确据尚未闭合 | **现有张力机制正确，但 claim 限定不足。** 不应自动合成一个公式。 | 补讨论层面、条件、后果、经文范围和被反对观点，进入专题审核队列。 |
| 整全人和死亡—复活阶段中的内外之人容易被关键词压平 | **现有关系足够，范围字段需加强。** | 保存生命阶段、术语所指、经文范围和反对的是哪一种固定模型。 |

这项复核把模型给出的三个 `major_change` 重新区分为：一个普查实现缺口、一个问题生命周期扩展、一个真正的教会领域候选扩展；不能把模型的严重程度直接当作架构结论。

## 四、完整语料揭示的设计与实现缺口

### 4.1. 第一遍普查必须保存经文的论证角色

205 篇中有 1,301 / 1,580 个内容群和 2,945 / 3,752 条主张带有经文引用，说明经文材料并不缺少。但是当前普查的 `scripture_refs` 只是原样字符串，没有稳定 OSIS，也没有角色。

因此，现阶段不能仅凭出现次数回答“教授重点释解了哪些经文”。同一个 `太 17:1` 可能是：

- 本讲主要解释的经文；
- 平行经文；
- 支持另一项神学主张的旁证；
- 历史背景；
- 教授反对的解释所引用的经文；
- 生活应用的根据。

总体设计中的 `ClaimRecord.bible_refs.role`、`ScriptureEvidence.role` 和 `PassageInterpretationChain` 已能承载这种区别，所以这不是知识模型需要推倒重做，而是普查 v2 必须补上的结构化采集：

```json
{
  "osis": "Matt.17.1-Matt.17.8",
  "display": "太 17:1–8",
  "role": "primary_passage",
  "scope_confidence": "high"
}
```

至少支持 `primary_passage`、`parallel_passage`、`lexical_support`、`historical_background`、`theological_support`、`counterexample` 和 `application_basis`。在此以前，只能发布“候选经文提及地图”，不能把它标作“释经覆盖地图”。

### 4.2. 来源必须保存可排序的讲道日期

项目要研究教授十五年以上的思想发展，就不能只靠文件名猜日期。现有 `SourceDocument` 有 `updated_at`，但缺少讲道事件本身的规范化日期。

需要增加：

- `delivered_at`：实际讲道或授课时间；
- `date_precision`：`exact`、`month`、`year` 或 `unknown`；
- `date_source`：网页元数据、文件名、系列资料或人工确认；
- `event_title`、`venue`、`series_title`；
- 原始日期文字，供日后复核。

没有这些字段，`ThoughtMapRevision` 只能记录编辑如何修改思想地图，不能可靠研究教授自己的思想是否随年代发展。

### 4.3. 文字定位与媒体时间定位必须分开表达

6,401 个文字 anchors 全部可回到逐字稿；但 93 篇 `reviewed` 来源的 3,212 个 anchors 没有媒体时间，另外 `published` 来源也有 35 个 anchors 暂无时间。

这不应使主张或来源失效。设计应明确：

- 精确文字高亮是来源有效性的最低要求；
- 媒体时间是可选的第二种定位能力；
- `time_status` 可为 `available`、`not_mapped`、`no_media` 或 `unknown`；
- 日后建立逐字稿—媒体时间映射时，可补时间而不改变 claim 或 citation ID。

### 4.4. 审核单位必须由交付物决定

3,752 条 candidate claims 和更多关系不适合逐条全库审批后才开始交付。设计中的 `DeliverableReviewScope` 是必要的，应成为默认工作流：

1. 为一项交付物建立 `CompositionPlan` 或问答需求；
2. 计算它真正依赖的最小 claim/evidence 子图；
3. 只把这组依赖变成人工审核任务；
4. 已审核记录回流知识库，供后续交付物复用；
5. 未进入任何交付物范围的 candidate 可以继续留在内部，不阻塞发布。

“够好可以发布”的门槛不是全库变绿，而是该交付物引用的实质主张、关系和来源全部达到它要求的审核状态。

## 五、对两类核心交付物的验证

### 5.1. 经文释经讲座

马太福音 17 章一类释经讲座需要：

- 以 `primary_passage` 和 `PassageInterpretationChain` 保持经文顺序；
- 从论证图选取解释本段所需的主张和证据步骤；
- 神学主题只展开到帮助理解当前经文的深度；
- 更完整的“人子”、信心、国度等论述链接主题专论；
- 教授没有讲解的经文标为资料缺口；
- 用 `CompositionDecision` 保存“详讲、略讲、转附录、链接主题、暂缓”的编辑判断。

### 5.2. 跨讲道主题专论

“人子”或“因信成义，而非因信称义”一类主题专论需要：

- 跨讲道合并相同命题，但保留新增理由、限定、反对观点和年代；
- 区分教授明确说出的主张、根据教授论证重建的结论，以及编辑综合；
- 显示每条主张的原始讲道、文字高亮和可用的媒体时间；
- 保存张力和变化，不为追求一篇流畅文章而提前消解；
- 由独立 `CompositionPlan` 决定论证顺序，而不是照讲道日期或某一篇讲道行程拼接。

两类作品使用同一知识基础，但不共享同一个篇章计划；这正是双轴和篇章编排层同时存在的理由。

## 六、验证后的优先修改顺序

1. 人工审核 17 个候选归组，重点决定“教会与服事”领域的层级，并复核三组未解决张力；
2. 将普查经文引用升级为带 OSIS 和角色的结构，生成真正的释经覆盖地图；
3. 为 `SourceDocument` 增加讲道日期与事件元数据；
4. 明确 citation 的文字定位与媒体时间定位能力；
5. 用马太 17 章释经讲座和“人子”主题专论验证最小可发布子图；
6. 测量这两个交付物的实际人工审核时间，再决定后续批次规模。

## 七、当前判定

**总体设计通过，但附带三项必须修正的条件：经文角色化、讲道日期规范化、按交付物审核。**

其中前两项是完整语料才暴露出来的数据基础问题；第三项是 3,752 条候选主张带来的编辑产能约束。任何一项不处理，系统仍可生成文章，却无法可靠回答“教授重点释解了哪些经文”“他的思想怎样发展”或“这个回答到底依据哪一组已审核证据”。
